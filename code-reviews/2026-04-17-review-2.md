## Risky Patterns

### 1. `ProjectSortOrderInput` is 1-indexed; DB `sortOrder` is 0-indexed — HIGH

**Files:**
- [`src/components/admin/ProjectSortOrderInput.tsx:18,30,62-63`](src/components/admin/ProjectSortOrderInput.tsx)
- [`src/components/admin/ProjectAdminControls.tsx:22-27`](src/components/admin/ProjectAdminControls.tsx)
- [`prisma/schema.prisma:47`](prisma/schema.prisma) — `sortOrder Int @default(0)`
- [`src/app/api/admin/projects/route.test.ts:133`](src/app/api/admin/projects/route.test.ts) — “With 5 existing projects at sortOrder 0..4, the new one slots in at 5”

`ProjectAdminControls` passes the raw DB `project.sortOrder` into `ProjectSortOrderInput` as both the initial value and the numeric inputs. The component then clamps on blur:

```ts
const clamped = Math.max(1, Math.min(totalCount, parsed))
```

and the `<input>` uses `min={1}` / `max={totalCount}`. But the database stores 0-indexed values (`@default(0)`, and new projects append at `count`, so a 5-project gallery has `sortOrder` 0..4). Concrete consequences:

- The top project (`sortOrder: 0`) displays `"0"` in the input. On any blur without the user touching it, `parseInt("0", 10) = 0` → clamped to `1` → a PUT fires with `{ sortOrder: 1 }`, swapping the project with its neighbour. A user who tabs through the admin gallery can silently reorder the top item.
- `max` is off by one: a 6-project gallery has valid DB indices 0..5, but the input accepts up to 6. Submitting `6` sends `{ sortOrder: 6 }` to the API, which shifts nothing (no project has `sortOrder > 5`), and the target project ends up at a value one past the last real row. The `$transaction` path in `src/app/api/admin/projects/[id]/route.ts:84-93` doesn't treat this as invalid — it happily writes the out-of-range `sortOrder`.
- Commit `a4601eb` ("Fix project sortOrder 0-indexing…") fixed the POST append path to use `count` (0-indexed), but this input predates that fix and was not updated to match.

**Options:**
- **(A) Shift the clamp to `[0, totalCount - 1]`** (min=0, max=totalCount-1). Smallest diff; keeps the "0 means first" DB convention visible to the admin. Best if you want the UI and DB to agree exactly.
- **(B) Display 1-indexed, translate at the boundary.** Render `initialSortOrder + 1`, clamp to `[1, totalCount]`, and subtract 1 before the PUT. Matches what a human expects when typing a position ("1st", "2nd"). Keyed remount via `key={${project.id}-${project.sortOrder}}` still works because the translation is local to the component.
- **(C) Do nothing.** Single-user site; the owner could avoid the issue by only clicking the arrow controls. Doesn't scale if a second editor is ever added.

**Recommended:** **(B)**. A sort-order input is a classic UX affordance for ordinal position; matching the DB's 0-index in the UI is the surprising choice. Translate once at the component boundary and the rest of the code stays 0-indexed.

**Resolved in Session 4** (commit `419595f`): went with (B). `ProjectSortOrderInput` now renders `initialSortOrder + 1`, clamps to `[1, totalCount]`, and subtracts 1 before the PUT. Also tightened the Zod `sortOrder` fields to `.min(0)` across all four project schemas (create/update + sections + links + images), and added `min={0}` to the `ProjectForm` sortOrder input so new-project entry can't send a negative value either.

### 2. `Project.sortOrder` has no unique constraint — MEDIUM

**Files:**
- [`prisma/schema.prisma:47`](prisma/schema.prisma)
- [`src/app/api/admin/projects/[id]/route.ts:64-94`](src/app/api/admin/projects/[id]/route.ts)
- [`src/app/api/admin/projects/route.ts:43-72`](src/app/api/admin/projects/route.ts)

The reorder logic in PUT/POST/DELETE assumes `sortOrder` is a dense 0-indexed sequence (no gaps, no duplicates). Every handler correctly maintains that invariant in isolation — the `$transaction` in PUT reads `current.sortOrder`, then shifts the affected half of the range. But:

- Prisma defaults to `READ COMMITTED` isolation. Two concurrent PUTs that both want to move different projects into the same target position both read a consistent pre-state, both compute different shift ranges, and both commit — producing duplicate `sortOrder` values with no error.
- There is no `@@unique([sortOrder])` on `Project`, so Postgres won't catch the race.
- DELETE's "close the gap" shift (line 156) assumes no duplicates exist at the decrement boundary; if invariant 1 is violated, this widens the damage.

On a single-user admin this is effectively unreachable, but the invariant is implicit. A transient admin-tab flapping between stale and fresh loads can produce the same duplicate-sortOrder end state, and because `getProjectsPage` orders by `[{sortOrder: "asc"}, {name: "asc"}]`, duplicates just silently tie-break on name — there is no failure signal.

**Options:**
- **(A) Add `@@unique([sortOrder])` in `schema.prisma`.** Any race surfaces as a Prisma `P2002` error in the transaction, which rolls back and the admin sees a "conflict, retry" message. Downside: adding this requires a migration (project uses `db:push`) and all the existing data would need `sortOrder` values verified as unique first. Also complicates the PUT transaction — the increment/decrement step briefly produces a duplicate between rows in the shift range, so the constraint would have to be `DEFERRABLE INITIALLY DEFERRED`, which Prisma's schema DSL doesn't express cleanly.
- **(B) Add a unit test that asserts the transaction preserves the "0..N-1 with no duplicates" invariant** across concurrent PUTs. Cheaper than a DB constraint but documents rather than enforces.
- **(C) Escalate isolation to `SERIALIZABLE` on this transaction path only.** Prisma supports `isolationLevel: Prisma.TransactionIsolationLevel.Serializable` on `$transaction`. Catches the race as a serialization error.
- **(D) Do nothing and document the assumption.** Flag it as a known single-editor invariant in the dev-journal or on the PUT handler itself.

**Recommended:** **(D)** for now, with an inline comment on the PUT transaction stating the single-writer invariant. Upgrade to (C) the moment a second admin account is added.

**Resolved in Session 4** (commit `2c2199e`): went with (D). Added a comment block above the `$transaction` in `src/app/api/admin/projects/[id]/route.ts` documenting the single-writer invariant, the READ COMMITTED + no-`@@unique` race window, and the escalation path to `Prisma.TransactionIsolationLevel.Serializable` if a second editor is ever added.

### 3. `defaultProto` returns http for any host with an explicit port — LOW

**File:** [`src/lib/request.ts:3-9`](src/lib/request.ts)

```ts
function defaultProto(host: string): "http" | "https" {
	if (host.startsWith("localhost") || host.includes(":")) {
		return "http"
	}

	return "https"
}
```

The `host.includes(":")` heuristic treats "has a port" as a proxy for "is development". But `host` here comes from `headers().get("host")`, which on Vercel is always the public hostname — in production the path is covered by `x-forwarded-proto` which takes precedence. The trap is any non-Vercel environment: reverse-proxying the app on `example.com:8443` over TLS without setting `x-forwarded-proto` generates `http://example.com:8443/...` URLs in `siteBase()`, which feeds into the Atom feed's `SITE_URL` and `post_urls`.

On the current Vercel deploy this never fires. It's a footgun for any future move to a different host.

**Options:**
- **(A) Remove the port heuristic; key only on `localhost`.** Safer default for production; developers running on `:3000` are still matched.
- **(B) Require `x-forwarded-proto`; throw if missing in non-local.** More explicit, but breaks local dev without a shim.
- **(C) Do nothing.** Current deploy doesn't hit the trap.

**Recommended:** **(A)**. One-line change, closes a real trap.

**Resolved in Session 4** (commit `5994371`): went with (A). `defaultProto` now returns `"http"` only when the host starts with `localhost` or `127.0.0.1`; every other host defaults to `"https"`. Non-Vercel deploys on explicit ports are no longer silently downgraded.

## Minor Notes

### Atom feed `<updated>` uses publish time, not modified time

**File:** [`src/app/api/feed/[section]/route.ts:74-77`](src/app/api/feed/[section]/route.ts)

```ts
const updatedAt =
    posts.length > 0
        ? postDatetimeToISO(posts[0].datetime)
        : new Date().toISOString()
```

`datetime` is the post's `yyyy-MM-dd-HHmm` publish stamp. An edit to the newest post bumps `updatedAt` on the `Post` row and invalidates the `feed-${section}` cache tag (so the feed does regenerate), but the new feed XML still advertises the old publish time as its `<updated>` value. RFC 4287 wants `<updated>` to reflect "the most recent instant in time when [the feed] was modified in a way the publisher considers significant" — an edit qualifies. Feed readers use this to decide whether to refetch.

Prefer `posts[0].updatedAt.toISOString()`, which is already selected by the Prisma query (visible on the entry `<updated>` at line 98).

**Resolved in Session 4** (commit `0b0ebbe`): feed-level `<updated>` now takes the `Math.max` of `post.updatedAt` across the feed entries, so an edit to *any* post (not just the newest) correctly advances the feed timestamp. Matches the entry-level `<updated>` semantics and the RFC 4287 intent.

### `ProjectForm` sortOrder input has no bounds

**File:** [`src/components/admin/ProjectForm.tsx:187-193`](src/components/admin/ProjectForm.tsx)

```tsx
<input
    id="sortOrder"
    type="number"
    value={sortOrder}
    onChange={(e) => setSortOrder(Number(e.target.value))}
    className="admin-input"

```

No `min`/`max`. Typing `-1` sets `sortOrder: -1` in state; on submit the API handler's POST path (`src/app/api/admin/projects/route.ts:43-49`) happily increments everything at `>= -1` (i.e., every project) and then inserts the new one at `-1`. Same story on PUT. Validation at the schema boundary would be the durable fix (`z.number().int().min(0)` in `projectCreateSchema`/`projectUpdateSchema`). Low real-world risk — the admin has to type a negative number on purpose — but it's a trivial add.

**Resolved in Session 4** (commit `419595f`, bundled with the sortOrder indexing fix): `ProjectForm` sortOrder input now has `min={0}`, and all four Zod schema `sortOrder` fields (project, section, image, link) require `z.number().int().min(0)`. Defence-in-depth at both the UI and API boundary — a negative value can't reach the handler.
