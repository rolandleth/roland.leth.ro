# Code Review — 2026-07-17

## Issues and Observations

- [x] **[src/lib/import/frontmatter.ts — `readField`/`unquote`]** — `readField` trims trailing whitespace before comparing, so `slug: hello ` (trailing space) parses to `"hello"` and `slugRewriteFor` sees `fileSlug === slug` → no rewrite planned. The on-disk file keeps drift that the "self-heal" narrative claims to erase. Fix: also plan a rewrite when the trimmed value differs from the raw remainder, or normalize on write-out. **Resolved 2026-07-17**: `slugRewriteFor` (and `slugInit.planStamp`) now compare `setFrontmatterSlug(content, slug) === content` — heals trailing space, quotes, and missing lines in one check, broader than the trim fix.
- [x] **[src/lib/import/postImport.ts — `resolveSlug` skip reason]** — A file with `slug:` present but empty reports `"Title produces an empty slug"`, identical to a file with no `slug:` line. The author whose blank field was ignored gets no signal. Retain raw-parsed value (empty string vs. null) and branch the message. **Resolved 2026-07-17**: `parseFrontmatter` keeps a blank `slug:` as `""` (was `null`); `emptySlugSkipReason` branches three ways.
- [x] **[scripts/init-post-slugs.ts:88 — `matchRow` datetime + title fallback]** — Datetime→row match binds a `length === 1` row even when the file's title disagrees (only a passive `(title differs from DB)` note is printed and the write proceeds); title fallback binds any file whose title collides with a row at a different datetime. A new file added post-import that shares a title with an existing row gets stamped with the wrong `slug:`; a subsequent `import-posts.ts --overwrite` then overwrites the wrong DB row with the new file's body. The tool never refuses a mismatched match. **Resolved 2026-07-17**: `matchRow` (now in `slugInit.ts`) binds a title fallback only for a row at the file's own datetime; a title match at a different datetime returns null → reported, not stamped. No flag. Datetime-match-title-differs still binds (safe) but surfaces in a distinct "eyeball these" report.
- [x] **[scripts/init-post-slugs.ts:33 — argv parsing / no unknown-flag guard]** — Unlike `import-posts.ts:68`, `init-post-slugs.ts` does not reject unknown flags. A typo (`--dryrun`, `--dry_run`, `--dry-Run`) is filtered out of `positionals` because it starts with `--`, but `argv.includes("--dry-run")` requires exact match — the script silently proceeds to rewrite files while the operator believes they are dry-running. High-blast-radius footgun on a bulk file-rewriter. **Resolved 2026-07-17**: added a `KNOWN_FLAGS` unknown-flag guard mirroring `import-posts.ts` — a typo'd flag now errors and exits before any write.
- [x] **[scripts/import-posts.ts — `applySlugRewrites`]** — `writeFile` isn't atomic; SIGKILL, out-of-disk, or a read-only-mount race mid-write leaves a truncated `.md`. The content repo is the source of truth here, so a partial write is worse than the DB errors the script defends against. `writeFile(tmp, …)` + `rename(tmp, final)` from `node:fs/promises` closes the window cheaply. **Resolved 2026-07-17**: shared `atomicWrite.ts:writeFileAtomic` (temp + rename, with temp cleanup on failure); both scripts write through it.

## Architecture

- [x] **[scripts/import-posts.ts — `main` sequence]** — `applySlugRewrites` runs before `planPostImport`, so a file whose body will later fail schema validation (>100 KB, empty section, etc.) still has its `slug:` line written to disk. Idempotent and low-blast-radius, but "dry-run reports the plan, then commit" is quietly weaker than the docstring implies; defer the write until after `planPostImport` skips, or note the ordering explicitly. **Resolved 2026-07-17**: kept the ordering (the slug is correct independent of body validation); documented it explicitly in the `import-posts.ts` header.

## Observability

- [x] **[scripts/import-posts.ts — `applySlugRewrites` failure path]** — A per-file `writeFile` rejection (EACCES on one file, EROFS on one mount) throws out of the loop into `main().catch`, killing every remaining rewrite and the DB step. Per-file try/catch with an end-of-run failure summary would let a partial batch proceed. **Resolved 2026-07-17**: `applySlugRewrites` (extracted to lib) captures each failure as a `"failed"` outcome; the script logs them, sets a non-zero exit, and the batch + DB import still run.
- [x] **[scripts/init-post-slugs.ts:272 — top-level `main().catch`]** — Errors surface only as `error.message` with no filename, phase, or already-written count. A mid-run permission failure leaves the operator unable to tell which file broke or which earlier files were already mutated; per-file logs stop mid-stream and only the tail exception remains. **Resolved 2026-07-17**: `stampFile` wraps read + write in try/catch, converting each I/O failure into a filename-tagged `problem`; the run continues and the summary counts written vs. problems, so per-file logs show what was already mutated.
- [x] **[scripts/init-post-slugs.ts:167 — `wrote … (title differs from DB)`]** — The most dangerous outcome (matched by datetime but title disagrees — the case likeliest to be a mismatch) is logged at the same visibility as a benign stamp. No warning prefix, no summary count, no non-zero exit. Should surface separately (like `problems`) or gate behind an explicit `--allow-title-mismatch` flag. **Resolved 2026-07-17**: with the `matchRow` guard, this case is no longer the dangerous one (the different-datetime match is now refused). Title-differs stamps surface in a distinct "eyeball these" section with a count; no non-zero exit, since it's the safe admin-edited-title case.

## Missing Tests

- [x] **[scripts/init-post-slugs.ts — entire file, ~275 LOC]** — Zero coverage. Untested branches include `matchRow` datetime-hit vs. title-fallback vs. ambiguous vs. null; `stampFile` for unparseable filename, missing `title:`, `fileSlug === row.slug` no-op, dry-run vs. write; `initFolder` fileless-rows path and problem-vs-write exit-code interaction; `resolveSection` folder-basename vs. `--section=` flag. Given the false-positive matching risk above, `matchRow` and the "title differs" branch are the load-bearing gaps. **Resolved 2026-07-17**: extracted the matching/planning core into `slugInit.ts` with 13 unit tests covering the `matchRow`/`planStamp` matrix (incl. the same-datetime disambiguation, the refused different-datetime match, and title-differs). `resolveSection`/`initFolder` I/O wiring stays in the untested shell.
- [x] **[scripts/import-posts.ts — `applySlugRewrites`]** — Not asserted anywhere: rewrite runs before any DB work and mutates source files unconditionally on non-dry-run. No test pins that a subsequent DB failure leaves file-side rewrites in place (documented as intended in the header comment) or that dry-run truly suppresses writes end-to-end. **Resolved 2026-07-17**: `applySlugRewrites.test.ts` (temp-dir) pins dry-run suppresses writes, non-dry-run applies atomically with no temp leftover, and per-file failure isolation. The "DB failure leaves rewrites in place" ordering stays a documented invariant, not a subprocess test.
- [x] **[src/lib/import/postImport.test.ts — `parsePostFiles`]** — No case exercising `slug:` present-but-empty (falls back to title, plans a rewrite with `previous: null`). `parseFrontmatter` covers it in isolation; the composed behavior is unpinned. **Resolved 2026-07-17**: added the blank-`slug:` case. Note `previous` is `""`, not `null` as guessed here — the blank field is now retained, so the rewrite log reads `slug: "" → x` rather than `(from title)`.
- [x] **[src/lib/import/postImport.test.ts — `parsePostFiles`]** — No CRLF-input fixture with a needed `slugRewrite` asserting the rewritten content preserves CRLF end-to-end. `setFrontmatterSlug` has the logic and a unit test, but no integration guarantee. **Resolved 2026-07-17**: added a CRLF fixture asserting the rewritten `slugRewrite.content` preserves CRLF end-to-end.
- [x] **[src/lib/import/frontmatter.test.ts — `setFrontmatterSlug`]** — Idempotency isn't asserted (`setFrontmatterSlug(setFrontmatterSlug(x, "a"), "a")` = single application). Guards against a regression that would make every re-run of the importer plan phantom rewrites. **Resolved 2026-07-17**: added idempotency + a byte-for-byte no-op-on-canonical test (the latter is the invariant the new rewrite check depends on).
- [x] **[src/lib/import/postImport.ts — `resolveSlug` idempotency invariant]** — No test pins `createSlug(createSlug(x)) === createSlug(x)` for the input class the canonical-shape check relies on (accented chars, dashes, `&`). Break the invariant for one input and every canonical file starts planning a phantom rewrite silently. **Resolved 2026-07-17**: added a parameterized `createSlug` idempotency test over accented chars, `&`, dashes, and punctuation.
- [x] **[src/lib/import/postImport.test.ts — `planPostImport`/`resolveOverwriteSummary`]** — Edge where DB summary was derived AND `next === existing.summary`: code returns undefined so no update is planned, but no test — a regression that always writes the summary back on a no-op change wouldn't trip the suite. **Resolved 2026-07-17**: added a test where bodies diverge only past the 160-char summary window — body updates, summary is omitted from the payload.

## Risk Assessment

**Medium.** The library refactor (shared `parsePostFiles` between admin bulk route and import script) is clean — it deletes a class of drift bug the admin route had actually regressed into, and the existing route tests held zero-modification against the new pipeline. The bulk route's concurrent-write reconciliation (`route.ts:186-199`) and its paired test are the strongest part of the diff. The risk sits entirely on the file-mutation surface: `init-post-slugs.ts` is a new ~275-LOC script with zero test coverage and two failure modes that silently write wrong data — the `matchRow` title-mismatch path (data-corrupting) and the typo'd `--dry-run` flag (footgun on a bulk rewriter). Neither has landed in production behavior, but the tool is intended to run against real content on demand, so both should be closed before the next resync.
