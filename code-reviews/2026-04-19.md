### 3. `lookupLegacySlug` caches `null` for draft slugs for up to 5 minutes after publish

**File:** [`src/lib/legacySlug.ts:39`](src/lib/legacySlug.ts)

The `unstable_cache` wrapper keys on the slug string with a 300s revalidate window. With `published: true` now in the query, a request for an as-yet-unpublished post's legacy slug will cache `null`. When the post is later published, any user or crawler hitting that slug within the 5-minute window gets a 404 (from the catch-all page's `notFound()` call) rather than the correct 308 redirect.

For a single-author blog where publish and legacy-URL setup are done together, this is low risk. The watch-out is the case where a post is pre-created with a slug that matches a historically-linked legacy URL and published later without a deploy. The 5-minute window is short enough to be acceptable; the main value in flagging it is so the invariant "new publish → wait up to 5 min for legacy redirect to activate" is explicitly known.

No code change required; worth adding to the Watch-outs section of the dev-journal if legacy redirects are ever documented as an explicit feature for readers to rely on.
