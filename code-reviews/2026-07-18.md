## Risk Assessment

**Medium.** The guides feature is a large, mostly clean addition — schema + data layer + admin CRUD + public pages + importer + integrations, all landing behind existing auth gates, with tests that pin the load-bearing behaviors (cross-table slug uniqueness, scheduled-guide filtering, published-topic drop, `changeFrequency` distinction from posts). The plumbing changes (detail-miss no longer cached, single-sourced detail tags, RevalidatePanel applied/skipped, middleware bot short-circuit + admin-gate tightening) also read as deliberate and well-tested. Risk concentrates in three places: (1) the `guideTag`/`guideTopicTag` namespace overlap, which is dormant today but a subtle correctness bug the moment a guide slug starts with `topic-`; (2) the `useAdminResource` save/remove race, which double-enables the submit button under legitimate impatient-user behavior and creates duplicate rows on rapid double-clicks; (3) the revalidate endpoint's silence on parent topic hubs — the very use case the panel exists for (post-script-import hub freshness) is the one it doesn't cover. None are catastrophic, none block ship; all three deserve close before the next content-heavy import cycle. Cross-cutting: four near-identical admin forms and four near-identical detail cache wrappers are drift bait; extracting an `AdminForm` shell and a `wrapNullableDetail` helper would pay for itself the moment a fifth resource lands.

**Skipped after investigation (with reasons):**
- `atomicWrite` fsync — narrowed the docstring instead; power-loss durability isn't worth an fsync-per-write on a dev-machine `.md` importer (SIGKILL/out-of-disk safety, what it needs, already holds).
- Misleading P2002 race messages — **false positive**: cross-table slug uniqueness is app-enforced (no cross-table DB constraint), so a P2002 only ever fires same-table; the "A guide/topic with this slug already exists" message is accurate for the race it catches.
- `describeGuideRefProblem` published-check — rejecting a guide→draft-topic attach would break the valid "publish guide before its topic" workflow, and the read path already drops the link gracefully; addressed the "invisible" concern via the draft-topic picker flag instead.
- `/api/admin/login` gate exemption — misleading: login lives at `/api/auth/login` (outside the gate) per convention; added a clarifying comment steering future login handlers away from `/api/admin/*` instead.
- App-level bot-404 logging — redundant with Vercel's platform request logs (path+status), and middleware is the hottest path the journal is CPU-conscious about.
- `import-guides` parallel file reads — unbounded `Promise.all` risks EMFILE at the "hundreds of files" scale the finding cited; a proper fix needs bounded concurrency, over-engineering for the current handful.
- `useAdminResource` RESOURCES-array — middleware gates all `/api/admin/*` generically, so there's no auth-drift risk and no clean single source across panel/hook.
- `loadGuide`/`loadGuideTopic` bare-form — kept the arrow form for consistency with `loadPost`/`loadProject`.
- module-load "no extra registrations" test — already covered by the existing exact `toEqual` snapshot.
- concurrent-miss cache test — would pin the test double's in-flight dedup, not production `unstable_cache` semantics.

**Discovered latent bug — since fixed (follow-up, 2026-07-18):**
- `src/lib/import/guideImport.ts — planGuide`: a guide file MOVED to a new folder with byte-identical content produced an empty `data`, was skipped as `UNCHANGED`, and its `topicId` was never re-resolved — the move silently didn't take. **Fixed**: `ExistingGuide` now carries the row's current `topicSlug`, and `planGuide` compares it against the file's folder-resolved target slug (`isTopicChanged`), forcing an update when they differ. Clean because the parser already skips any guide whose folder lacks an `index.md`, so a grouped guide's folder always resolves to a parsed topic slug — no unresolvable edge. The shell's update path already applies `topicId` from the folder, so no apply change was needed; the plan log labels a topic-only update `(topic)`.
