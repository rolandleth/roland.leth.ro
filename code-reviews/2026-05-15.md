## Issues and Observations

- **[src/lib/posts.ts — split publish contract]** — two parallel publish gates now exist: `publishedWhere(section, now)` at the DB layer and `post.datetime <= now` at read-time (after cache return). The read-time half is duplicated in 5+ places (`getPostsBySection`, `getPostBySlug`, `getPostsGroupedByYear`, `getAllPublishedPostSlugs`, `lookupLegacySlug`, feed handler). Any future query that forgets the read-time filter will silently leak scheduled posts via the cache. Extract a single `isLive(post, now)` predicate and route every cached read through it.
- **[src/lib/posts.ts — `getPostsBySection` page 1 vs page>1]** — page 1 reads from `unstable_cache` padded with `futureCount` then filters at read time; page>1 issues a fresh `now`-filtered DB query with `skip: PAGE_SIZE`. If a scheduled post crosses `now()` mid-session, it can appear on **both** page 1 (from cached padding that just became live) and page 2 (because `skip` shifts by one). Real but rare UX bug; pin behavior with a test and either snap the read-time filter to a per-request `now` shared with the page>1 `skip`, or filter both pages identically.
- **[src/lib/posts.ts — `getPostsBySection` multiple `now` reads]** — three independent `currentDatetimeString()` calls per page-1 request (cache-fn `futureCount`, where-clause, read-time filter). Across a minute boundary, the `count`-driven `totalPages` can include a row the read-time filter excludes, producing an empty last page. Hoist one `now` at the entry point and pass it through.
- **[src/lib/posts.ts — `getPostBySlug` future bodies in cache]** — `unstable_cache` now stores the full `PostDetail` (including potentially large `body`) for future-dated rows the user can't see yet. Minor cache bloat; exposes draft content to anyone with cache-dump access.
- [x] **[src/lib/keepalive.ts — under-abstracted module]** — file is named like a helper but exports only a constant. The actual write logic (`new Date().toISOString()` + `redis.set` + try/catch + log) is copy-pasted across `src/app/api/cron/ping/route.ts` and `src/app/api/admin/keepalive/route.ts`, and the two log shapes have **already drifted** (cron logs bare `result.error`, admin logs raw `error`; cron has no success line, admin has `console.info`) — exactly the drift the 2026-05-14 dev-journal predicted. Extract `writeKeepalive(redis)` returning a discriminated result; each caller picks its own status code / log tag. **Resolved 2026-05-15**: extracted `writeKeepalive(redis): KeepaliveResult` (discriminated `{ ok: true; value } | { ok: false; error }`) into `src/lib/keepalive.ts`; both routes consume it and own their own log tag + status code shape (cron 200 on no-Redis, admin 503; both 502 on `redis.set` reject). The drift the 2026-05-14 watch-out predicted is closed at the source.
- **[src/app/api/auth/login/route.ts — `clientBucketKey` computed twice per failed login]** — once for the limiter, again for the warn log. Two HMAC-SHA256 calls per request where one suffices. Hoist once at the top of `POST`.
- **[src/app/api/auth/login/route.ts — `slice(0, 22)` magic constant]** — 22 base64url chars (132 bits) is fine for collision space but undocumented. Extract `IP_HASH_TRUNCATION = 22` or comment why 22.
- **[src/lib/env.ts — `getIpHashSecret` accepts any non-empty string]** — a 1-byte secret passes. HMAC-SHA256 keys should be ≥32 bytes; a typo'd 4-char secret yields a trivially-brute-forceable HMAC and silently re-opens the rainbow-table vector the secret was added to close. Add `z.string().min(32)` (or warn-and-null below the floor).

## Architecture & Coupling

- **[src/lib/posts.ts — `take: PAGE_SIZE + futureCount` padding sizing]** — assumes `futureCount` is small (true for one author). No upper bound: bulk-importing N future-dated posts inflates every cached page-1 payload linearly. Add `Math.min(futureCount, MAX_PAD)` or at minimum a comment pinning the assumption to single-author volume.
- **[src/app/api/feed/[section]/route.ts — cache-padding pattern duplicated]** — same `take: LIMIT + futureCount` shape as `posts.ts`. Extract a `cachedWithFutureWindow` helper once a third caller emerges (rule-of-three); flagging now so it's not forgotten.
- **[src/lib/keepalive.ts]** — see Issues. Either promote to a real helper module or rename to `keepaliveKey.ts` to signal "constant only."

## Observability

- **[src/lib/posts.ts — silent under-pad in cached page 1]** — when a scheduled post is added between cache populate and request, `futureCount` from the cached miss underestimates and the read-time filter can shrink the page below `PAGE_SIZE` with no DB fallback and no log. A debug line when `cached.length - futures > 0 && filtered.length < PAGE_SIZE` would surface this in prod.
- **[src/app/api/cron/ping/route.ts vs src/app/api/admin/keepalive/route.ts — drifted log shapes]** — see Issues. Consolidating the write closes the observability gap as a side effect.
- **[src/app/api/auth/login/route.ts — module-load warn for missing IP_HASH_SECRET]** — emits only on cold start (top-level `console.warn`). The 2026-05-14 journal claim that it's "discoverable from function logs" is technically true but overstates frequency; warm invocations never re-emit. Consider a once-per-N-minute lazy warn at the rate-limit gate, or accept cold-start-only and update the journal note.

## Performance

- **[src/lib/posts.ts — uncached page-1 count]** — `prisma.post.count({ where: publishedWhere(section, now) })` runs per request on the hottest route (the request-time `now` defeats caching). With the existing composite index Postgres range-scans cheaply, but it's a roundtrip the old design avoided. Acceptable; flagging because it offsets some of the caching gain.
- **[src/app/api/feed/[section]/route.ts — markdown rendering for future rows]** — markdown render runs over future-dated rows pulled in for the padding window (acknowledged in code comment). Fine for 1–2 scheduled posts; scales linearly with scheduled-backlog size if that ever changes.

## Risk Assessment

**Medium.** Time-based scheduled publishing is the load-bearing change: it widens the publish-state contract into a two-layer filter (DB + read-time) and the read-time half is now duplicated across six call sites with no shared helper. The same query forgetting the read-time filter is the silent-leak shape — high consequence, low probability today, but the surface area grows with every new cached read. Page 1 vs page>1 boundary handling has a real but narrow duplicate-row bug at the moment a scheduled post crosses `now()`. The rate-limit / keepalive commit is mostly correct, but `IP_HASH_SECRET` size is unvalidated (a 4-char secret silently weakens the GDPR-posture fix), and the keepalive "helper" module already exhibits the log-shape drift the dev-journal predicted on the day of merge. Vitest pin and `prefetch={false}` are low-risk defensive changes.
