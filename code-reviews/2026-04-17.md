## Risky Patterns

### 1. Legacy redirect returns raw JSON 404 — UX regression

**File:** [`src/app/api/legacy-redirect/[slug]/route.ts:80`](src/app/api/legacy-redirect/[slug]/route.ts)

The `/404`-redirect loop was correctly fixed, but the replacement is a JSON response:

```ts
return NextResponse.json({ error: "Not found" }, { status: 404 })
```

When middleware rewrites `/unknown-slug` to this API route, the browser receives the raw JSON body — not the styled 404 page. A visitor hitting any unknown root-level URL (e.g. a broken backlink) now sees `{"error":"Not found"}` rather than a page.

**Options:**
- Return `NextResponse.rewrite(new URL("/not-found", request.url))` if Next.js allows rewriting to a non-found page from an API route.
- Or move the "is this a legacy slug?" check into `src/proxy.ts` itself — only rewrite to the handler if a header/cookie cache says the slug _might_ be legacy, and fall through to Next.js otherwise.
- Or add `/404` to `KNOWN_ROUTES` (it would no longer be intercepted as a legacy slug attempt). Simplest, but `/404` is not an App Router route either — the correct path is `/not-found` in the app directory or a thrown `notFound()`.

**Recommended:** Check whether Next.js `notFound()` can be called from an API route, or rewrite to `/not-found` from the API handler.

**Resolved in Session 3.** Moved the lookup out of the API route and into a root-level catch-all page (`src/app/[slug]/page.tsx`). On hit: `permanentRedirect` (308, preserves the old 301-as-permanent signal). On miss: `notFound()`, which renders `src/app/not-found.tsx` with full site chrome. The API route + middleware rewrite are both deleted; Next.js' static-over-dynamic dispatch takes care of known routes falling through without a reroute.

### 2. `KNOWN_ROUTES` has no enforcement mechanism

**File:** [`src/proxy.ts:8`](src/proxy.ts)

```ts
// Must be kept in sync with the top-level folders under `src/app/`
const KNOWN_ROUTES = new Set(["/about", "/admin", "/api", "/blog", "/privacy", "/projects", "/tools"])
```

A new top-level page (e.g. `/changelog`, `/resume`) that isn't added here gets silently rewritten to the legacy-redirect handler and 404s. The comment is correct but unenforceable.

**Options:**
- Add a proxy test that cross-checks `KNOWN_ROUTES` against the filesystem (`glob("src/app/*/")`) — catches the gap at CI time.
- Or move the check to an allowlist-inverted pattern: only rewrite to the legacy handler for single-segment paths that don't match a Next.js route (harder to implement but self-maintaining).

**Recommended:** Add a `src/proxy.test.ts` case that loads actual `src/app/` subdirectories and asserts each is either in `KNOWN_ROUTES` or a known exception.

**Resolved in Session 3.** Dissolved the whole class of bug: the catch-all page (`src/app/[slug]/page.tsx`) is only reached when Next.js has already ruled out every static top-level route, so there's no allowlist to maintain. `KNOWN_ROUTES` is gone; `proxy.ts` returns `NextResponse.next()` and lets routing handle the rest. As a side effect, the cognitive-complexity lint warning on `proxy.ts` (16 > 15) dropped back under the limit.

### 3. `Section` enum migration is a deploy-time prerequisite

**Files:** [`prisma/schema.prisma:17`](prisma/schema.prisma), [`src/lib/posts.ts:34`](src/lib/posts.ts)

The generated Prisma client now types `post.section` as `Section` (the enum), but this is only valid after `yarn db:push` (or a migration) runs against the live database. Deploying the new client before the schema migration will cause runtime type mismatches if Prisma validates enum membership, or quietly pass through if it doesn't — either way, it's fragile.

No migration file exists in `prisma/migrations/` (project uses `db:push`). The deploy checklist should explicitly gate on the push completing first.

**No code change needed**, but this should be tracked as a deploy gate — run `yarn db:push` before the app goes live on this commit.

**Still open as a deploy gate.** No code change this session; the push ordering is on the human deploying the `release` branch.
