## Issues and Observations

- **src/app/api/auth/login/route.ts — `clientBucketKey()`**: Falls back to literal `"unknown"` when `x-forwarded-for` is absent, collapsing all header-less requests into one shared bucket — defeats per-IP rate limiting in any environment without a proxy setting that header (direct Vercel hits during development, curl, misconfigured CDN).
- **src/components/admin/AdminNav.tsx — `handleLogout`**: 401 and 500 collapsed into the same retry-shaped message. On 401 the session is already gone and the user should be redirected, not invited to retry.
- **src/lib/platforms.ts — `hasKeyword`**: `\b…\b` is wrong for keywords with leading/trailing non-word characters (`react-native`, `.net`, `c++`). Word boundaries anchor at letter/digit edges — for hyphenated or punctuated keywords, use lookarounds keyed on whitespace/string boundaries instead.
- **src/lib/analytics.ts — `filterAdminEvents` URL fallback**: For a relative URL containing `#` but no `?`, `split('?')[0]` returns the path-with-fragment; the admin-path anchor check then sees the fragment and can mis-classify. Strip `#` from the result or use `new URL(url, "http://x")` for guaranteed parsing.

## Architecture & Coupling

- **src/lib/projects.ts — `revalidateProject`**: A slug-changing PUT must call this twice (old slug, then new slug) — contract is implicit and comment-only. Accepting both old and new slug in the signature, or asserting the double-call at the route handler, would make the invariant enforceable.

## Observability

- **src/app/api/auth/login/route.ts — Redis fail-open**: Correct posture, but the `console.warn` is not tagged distinctly enough to alert on. A sustained Redis outage means unlimited login attempts with no operator-visible signal beyond log volume.
- **src/app/api/auth/login/route.ts — schema validation log at `console.warn`**: Brute-force probing of the login endpoint won't surface in error dashboards that filter on `console.error`. Confirm this downgrade is intentional given the security context.
- **src/app/api/upload/route.ts — upload 500 path**: Returns generic "Upload failed" with no `requestId` in the response body — inconsistent with `respondInternalError()` used everywhere else; blocks user-side correlation when reporting failures.
- **src/lib/auth.ts — JWT error split**: `ERR_JWT_EXPIRED` → info, others → error is a sound split, but verify that the jose codes on malformed/signature-mismatch failures carry a `.code` field; jose throws a plain `Error` for some modes and those would fall to the error branch only if the type guard is exhaustive.
- **src/components/admin/ProjectSortOrderInput.tsx — failure path**: Swallows HTTP status entirely (only "Failed to save" rendered, nothing logged) — a 409 from the API is indistinguishable from a network drop. `useAdminResource`'s `readErrorMessage` pattern already solves this; reuse it.

## Concurrency & Thread Safety

- **src/app/api/admin/posts/[id]/route.ts — cross-section cache bust**: Reading the previous section and then executing the UPDATE are two statements. Without wrapping them in a single transaction, a concurrent update between the two reads stale section data. Low severity if stale-cache-only, but worth a comment or a transaction wrapper.
- **src/app/api/admin/projects/[id]/route.ts — serializable storm**: Two concurrent PUTs on different projects targeting the same `sortOrder` can both retry under serializable isolation. Confirm there is a retry/abort policy and that the client surfaces 409 or 503 rather than hanging or silently losing one write.
- **src/components/admin/IsFeaturedToggle.tsx — rapid toggle**: Abort + optimistic-revert order is not covered. If the abort races a server commit, local state and server state diverge silently. Verify the post-abort state reconciles with the latest user intent (refetch on settle or a request queue).

## Risk Assessment

**Medium.** This is a substantial batch covering security-adjacent plumbing (rate limiting, auth, upload, cross-section cache invalidation) alongside admin UX polish and test infrastructure. The high-level design is sound and the concurrency patterns (serializable transactions, AbortController, mount guards) are correctly applied. The main elevated risk is `clientBucketKey` sharing one `"unknown"` bucket for header-less requests — a deployment without `x-forwarded-for` loses per-IP bucketing entirely and the current test suite wouldn't catch it. The `handleLogout` 401-vs-500 distinction is a low-severity UX correctness issue. Nothing landed that directly breaks existing contracts, but the missing rejection-case tests for `postDatetime`, `sanitizeFilename`, and `clientBucketKey` leave the new validation logic without regression anchors.
