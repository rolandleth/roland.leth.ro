# Code Review — 2026-04-21

## Issues and Observations

- **src/lib/markdown.ts — extractText (image nodes)** ✅ fixed — mdast `image` nodes store alt text in an `alt` property, not in `value` or `children`. `extractText` returns `""` for them, so any post where an image's alt text provides narrative context produces a gap in the `stripMarkdown` output. Feed summaries for image-heavy posts could be incomplete or misleading with no error or warning surfaced. `extractText` now returns `node.alt ?? ""` for both `image` and `imageReference`.

- **src/app/api/feed/[section]/route.ts — cache payload size** — The cached payload now includes the full rendered `htmlBody` for each of up to 20 posts. Long posts can be many KB each, and the payload is duplicated per section. Not a correctness issue, but worth monitoring Next.js cache memory after the first deploy with production post lengths.

## Missing Tests

- **src/lib/markdown.ts — stripMarkdown (image alt text)** ✅ added — No test exercises `![Alt text](url)`. A test documenting the expected behavior (preserve or omit alt text) would both catch the current silent drop and lock in intent if the function is updated. Three tests added: inline image alt, image reference alt, empty-alt returns empty string.

## Risk Assessment

**Low–Medium.** The feed now serves full HTML post bodies in `<content type="html">`, which is the correct Atom pattern and a genuine improvement for feed readers. The markdown pipeline split — Shiki-free `htmlProcessor` for feeds, Shiki `markdownProcessor` for blog pages — is clean, well-commented, and the three module-level singleton processors avoid per-call allocation on hot paths. Test coverage for the route and `stripMarkdown`/`markdownToHtml` is solid. The main risks are (1) the image alt text drop in `stripMarkdown`, which is a silent correctness issue for posts with meaningful alt text; (2) cache payload size growth under real post lengths.

## Review 2

### Issues and Observations

- **src/app/api/feed/[section]/route.ts — `<![CDATA[${post.htmlBody}]]>`** ✅ fixed — if any rendered post body ever contains the literal sequence `]]>` (e.g. a code block demonstrating XML/CDATA, a quoted CDATA example, or a string like `array[i]]]>foo`), the CDATA section terminates mid-content and the feed becomes malformed XML. Canonical mitigation is `htmlBody.replace(/\]\]>/g, "]]]]><![CDATA[>")` before interpolation. Low probability in practice for a personal blog, but silent and total — the feed breaks for every reader on the first offending post. `escapeCdata` helper added; applied before CDATA wrapping.

- **src/lib/markdown.ts — `extractText` also drops `imageReference` alt** ✅ fixed — same shape as `image` (alt lives outside `value`/`children`); the finding above implicitly covers it but it's worth naming since `![alt][ref]` is a less obvious path to the same silent drop. Covered by the same `image`/`imageReference` branch in `extractText`.

- **src/lib/markdown.ts — `stripMarkdown` cast `as unknown as MdastNode`** ✅ fixed — the double cast loses the type safety `@types/mdast` / `mdast` would provide. `unified().parse()` returns `Root`; importing the type from `mdast` (already transitively present via `remark-parse`) removes both casts and the local `MdastNode` shim, and would make the `image`/`imageReference` gap surface as a type-level hint next time this function is touched. Replaced with `Nodes` import from `mdast`; local shim deleted; cast removed.

### Missing Tests

- **src/app/api/feed/[section]/route.test.ts — CDATA escape behavior** ✅ added — no test feeds a body whose rendered HTML contains `]]>`. Add one that asserts either the sequence is escaped or the feed is still well-formed XML (e.g. via a minimal parse assertion). Pairs with the Issue above.

- **src/lib/markdown.test.ts — raw HTML passthrough** ✅ added (as drop-not-passthrough) — `markdownToHtml` uses `remark-rehype` without `rehype-sanitize`, so raw HTML in post bodies (including `<script>`) flows straight into `<content>`. Worth a test that documents the current contract (passthrough, trusted-input assumption) so a future reader doesn't assume sanitization is happening. **Investigation revealed the actual contract is stricter**: `remark-rehype` drops raw HTML by default (no `allowDangerousHtml`). Test now asserts the drop, which is a safer contract to lock in.

### Notes

- Image alt text drop in `stripMarkdown` is currently only a feed-summary concern (no other caller strips markdown), so impact is bounded to Atom `<summary>` blurbs.
- Feed cache size watch-out from Review 1 is also worth a line in the dev-journal Watch-outs section if this review is accepted — currently only captured here.
