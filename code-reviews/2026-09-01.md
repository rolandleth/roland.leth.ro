Scope: `8bc9132`, `d2a607d`, `09fff0d`, `5c920c7`, `b6ca1da` — scheduled posts serve a

## Issues and Observations

- [x] **`src/components/blog/ScheduledPostNotice.tsx:37` — `max-w-m`** — `b6ca1da` turned
  `max-w-md` into `max-w-m`, which Tailwind v4 resolves against the `--container-*`
  namespace; no `--container-m` exists in `globals.css`, so the class emitted nothing and
  the body copy ran to the parent's `max-w-4xl`. **Resolved in the working tree** as
  `max-w-lg`, uncommitted at review time. **Resolved 2026-09-01**: corrected by hand to
  `max-w-lg`.
- [x] **`src/lib/utils/format.ts:159` — `formatDayMonth`** — byte-identical to `formatDate`
  except for the omitted `year` option: same regex match, same guard, same local-midnight
  `Date` construction. Its own docblock says "Same parsing and calendar-day semantics as
  `formatDate`", which is the DRY case stated out loud. Contrast `formatDateValue`
  directly below, whose docblock argues a real reason *not* to share. A private helper
  taking `Intl.DateTimeFormatOptions` collapses both. **Resolved 2026-09-01**: both now call
  a private `formatCalendarDay(datetime, options)`.
- [x] **`src/app/api/blog/[section]/[slug]/md/route.ts:78` — scheduled stub body** — the real
  export is self-describing (`buildPostMarkdownFile` emits `title`/`slug`/`section`/`date`/
  `canonical` frontmatter); the stub emits a bare `# Title` with no frontmatter under the
  same `text/markdown` content type. A consumer keying on frontmatter can't tell a
  scheduled stub from a malformed export, and one keying on the body reads "Scheduled:
  this post goes live on …" as the post's content. `X-Robots-Tag` reaches search crawlers
  only, not an agent fetching the URL directly. A frontmatter block carrying `scheduled:
  true` + `date:` would make it self-describing in the route's own idiom. **Resolved
  2026-09-01**: `buildScheduledPostMarkdownFile` shares `postFrontmatterLines` with the live
  export and appends `scheduled: true`.

## Architecture & Coupling

- [x] **`src/app/blog/[section]/[slug]/page.tsx:52` — scheduled metadata bypasses
  `buildPageMetadata`** — the branch returns `{ title, robots }` only, so it emits no
  `alternates` and inherits the root layout's, which hard-codes the **tech** feed. On a
  scheduled `/blog/life/:slug`, the page's `<link rel="alternate" type="application/atom+xml">`
  advertises the tech feed while the notice's own visible "the feed" link
  (`feedLinkForSection(section)`) points at the life feed. Same page, two different feeds.
  **Resolved 2026-09-01**: the branch routes through `buildPageMetadata` with
  `feed: feedLinkForSection(section)`.
- **Guides have no equivalent notice** — `src/app/guides/[slug]/page.tsx:130` still
  `notFound()`s a scheduled guide. Correctness is unaffected (guides carry their own
  `revalidatePostDetails` counterpart, `src/lib/db/guides.ts:581`), so this is a UX
  asymmetry rather than a defect — flagged as an observation, not a request to widen scope.

## Concurrency & Thread Safety

- [x] **`src/lib/db/posts.ts:340` + `:378` — two independent clock reads per miss** —
  `getPostBySlug` and `getScheduledPost` each call `currentDatetimeString()`. On the miss
  path both run in the same render, so a post crossing its `datetime` between the two calls
  makes `loadPost` return `null` (still scheduled) and `loadScheduledPost` also return
  `null` (already live), falling through to `notFound()` — the pinned 404 this feature
  exists to remove. The window is microseconds wide and must straddle exactly that post's
  minute boundary, and the next cron run heals it within the normal ~25h, so the impact
  ceiling is the old behaviour on one post. Cheap to close by resolving the row once and
  branching on a single `now`. **Resolved 2026-09-01**: `resolvePost` reads the row and the
  clock once and returns a `PostResolution` union.

## Observability

- [x] **Stale notices are now invisible** — a scheduled URL that outlives its date used to
  serve a 404, which surfaces in Vercel analytics and Search Console as an error. It now
  serves a 200 that looks like an ordinary pageview. Self-healing is unchanged, but if the
  cron silently stops (no retry, best-effort delivery), nothing signals that a post is
  stuck behind its own notice. This is the detection half of the publish-day window already
  logged as a watch-out. **Withdrawn 2026-09-01**: the finding was wrong. The cron already
  logs a heartbeat on its quiet path for this exact purpose
  (`src/app/api/cron/revalidate-scheduled/route.ts:266`), and a pinned prerendered page runs
  no code, so the cron is the only layer where detection can live.

## Risk Assessment

**Low.** The change is well-scoped and lands on plumbing that was already documented in
detail. The load-bearing decision — split the row fetch into `fetchPostRow` and keep the
clock verdict at the callers — is the right one and is confirmed by `wrapNullableDetail`'s
own docblock, which states that read-time clock filters belong at the call site. Both
callers share one cache entry and one tag set, so live and scheduled views cannot disagree
about the row, and no new invalidation machinery was introduced. Contracts widened in two
places that deserve naming: `/blog/:section/:slug` and its `.md` twin now return 200 with a
title and date where they previously returned 404, so a scheduled post's title and publish
date are public at a guessable URL (drafts stay hidden — `published: true` is enforced at
the query boundary and pinned by a test). The alias-before-scheduled ordering on the miss
path is correct and tested. Targeted suites (189 tests), `tsc --noEmit`, and `yarn lint` all
pass. What warrants caution is the follow-up commits: `5c920c7` and `b6ca1da` were pure
visual tuning with no test to catch the `max-w-md` → `max-w-m` slip, and that class silently
does nothing rather than failing anywhere.

## Resolution

Fixed in the same session, uncommitted at time of writing.

- **`max-w-m`** — corrected to `max-w-lg` by hand before the fixes started.
- **`formatDayMonth` duplication** — both formatters now call a private
  `formatCalendarDay(datetime, options)` in `src/lib/utils/format.ts`, holding the regex,
  the fallback, and the local-midnight `Date`. `formatDateValue` stays separate for the
  reason its own docblock gives.
- **`.md` stub frontmatter** — new `buildScheduledPostMarkdownFile` in
  `src/lib/content/postMarkdown.ts`, sharing `postFrontmatterLines` with the live export so
  the stub carries the same keys plus `scheduled: true`, and a title with a `"` in it is
  escaped on both paths. The route no longer hand-rolls the body.
- **Feed disagreement** — the scheduled metadata branch routes through
  `buildPageMetadata` with `feed: feedLinkForSection(section)`, so a scheduled
  `/blog/life/:slug` advertises the life feed. It also gains a real OG title instead of
  the layout's generic card. `description` and `markdownPath` stay omitted: the tease is
  title-only, and the `.md` twin is a stub rather than a markdown view of the page.
- **Double clock read** — replaced by `resolvePost` in `src/lib/db/posts.ts`, returning a
  `PostResolution` discriminated union from one row fetch and one `currentDatetimeString()`.
  The comparison moved onto the existing `isFutureDatetime` helper, whose docblock already
  argued for a single captured `now`, so live and scheduled are complements by
  construction. `loadPostResolution` (React-cached) is what both detail routes read, which
  also stops `generateMetadata` and the page body from reaching independent verdicts.
  `loadPost`, `getScheduledPost`, and `loadScheduledPost` lost their last callers and were
  removed; `getPostBySlug` stays as the narrow live-only accessor and now delegates.
- **Missing tests** — added `src/components/blog/ScheduledPostNotice.test.tsx` (5 tests,
  including a parameterized pair asserting both section-dependent hrefs), a
  `datetime === now` boundary pair under fake timers in `posts.test.ts`, and route-level
  tests for the stub's frontmatter and its YAML escaping.

**Observability finding withdrawn.** The cron already emits a positive heartbeat on its
quiet path (`src/app/api/cron/revalidate-scheduled/route.ts:266`), and its comment states
the exact purpose: making "nothing came due" distinguishable from "this cron stopped
running". That is the only layer where the detection can live, since a pinned prerendered
page executes no code and cannot report on itself. Nothing to build.
