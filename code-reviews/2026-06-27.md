# Code Review — 2026-06-27

Scope: commits `bfac1a0` (wrap-up) and `f659263` (project gallery overhaul). Source delta is the gallery feature: `ProjectContent.tsx`, `ProjectImageLightbox.tsx` (new), `ProjectSectionCarousel.tsx`, `useScrollOverflow.ts` (new), and their tests.

## Issues and Observations

- **`src/components/projects/ProjectImageLightbox.tsx` — `useEffect` keyboard handler** — deps include `onClose`/`onPrev`/`onNext`, which `ProjectContent` re-creates as fresh arrow functions on every render. The effect detaches and reattaches the `window` `keydown` listener each parent render while the lightbox is open. Not a correctness bug, but wrapping the three handlers in `useCallback` (or moving the handlers into a ref) would stop the per-render listener churn.
- **`src/components/ui/useScrollOverflow.ts` — `node` captured at effect time** — if `ref.current` is reassigned to a different element while the `RefObject` identity stays stable (e.g. a callsite that conditionally re-mounts the scroller), the listeners stay attached to the old node and the new one is never wired up. Current consumer (`ProjectContent`'s tablist ref) doesn't trigger this, but the hook is a reusable primitive and the limitation isn't documented.
- **`src/components/projects/ProjectContent.tsx` — defensive bounds** — `imageIndex` is parent-owned and always paired with `setActiveTab`, so today `activeSection.images[imageIndex]` is in-range. There's no guard if a future code path advances `imageIndex` without resetting on tab change; the carousel's `current = images[index]` would crash on `current.url`. Cheap to add an `index = Math.min(imageIndex, images.length - 1)` clamp in the carousel as a contract backstop, matching the existing `images.length === 0` guard.

## Architecture & Coupling

- **`src/components/projects/ProjectContent.tsx`** — now owns 4 `useState` + 3 `useRef` + 2 `useEffect` plus the cross-section navigation logic (`findAdjacentImageSection`, `navigateImage`, `goToSection`, `selectImage`, `selectTab`, `handleTabKeyDown`) and threads index/direction/handlers to two children. Lifting was the right call to share one gallery position, but the component is now load-bearing and ~430 lines. A `useProjectGallery(sections)` hook returning `{activeTab, imageIndex, slideDirection, isLightboxOpen, …handlers}` would isolate the state machine and shrink the view component.
- **`src/components/projects/ProjectSectionCarousel.tsx` — controlled-component contract** — now requires `index`, `direction`, `onSelectImage`, `onEnlarge`. The new shape is cohesive with `ProjectContent`'s ownership but any future reuse outside that parent has to replicate the same plumbing. Worth a one-liner in the file header documenting that the carousel is intentionally headless and assumes a host that owns the gallery position.

## Performance

- **`src/components/projects/ProjectContent.tsx` — `sectionsWithImages`** — `sections.filter(s => s.images.length > 0).length` runs on every render to derive `canNavigateGallery`. Trivial for current section counts, but cheap to memoise or short-circuit (e.g. `sections.some((s, i) => i !== activeTab && s.images.length > 0)`), and would also make `canNavigateGallery` reflect "is there *anywhere else* to go" more precisely than the current `> 1` count.

## Missing Tests

- **`src/components/projects/ProjectImageLightbox.test.tsx` — Tab focus-trap** — `trapTabFocus` is implemented but no test asserts that Shift+Tab from the first focusable wraps to the last (or vice versa). Real keyboard-trap regressions wouldn't be caught.
- **`src/components/projects/ProjectImageLightbox.test.tsx` — body scroll lock + focus restore** — both side-effects are implemented (`document.body.style.overflow`, restoring focus to the previously focused element) but unasserted. Either could silently regress; both are testable in happy-dom.
- **`src/components/ui/useScrollOverflow.test.tsx` — `ResizeObserver` path** — deliberately stubbed to a noop so only the scroll path is exercised. The "size changed without a scroll event" path (the whole reason `ResizeObserver` is in the hook) has no coverage — a regression that drops the observer wiring would pass.
- **Global-state pollution across test files** — `useScrollOverflow.test.tsx` uses `vi.stubGlobal("ResizeObserver", …)` in `beforeAll` with no `afterAll(() => vi.unstubAllGlobals())`; `ProjectContent.test.tsx` assigns `HTMLElement.prototype.scrollIntoView = () => {}` and never restores it. Both leak past the file boundary unless Vitest is configured with `unstubGlobals: true`. Either restore in an `afterAll` or move to `vi.spyOn` so the test runner handles teardown.

## Risk Assessment

**Low–Medium.** The feature delta is well-tested (1180-test suite green, tsc + lint clean per the journal), the controlled-component refactor is internally consistent, and the two real footguns the session encountered (ref-stability infinite loop, corner halo from `object-contain` not rounding the visible image) are already hardened and documented as watch-outs. What raises it from Low is scope: this is a new user-facing surface (portal-mounted lightbox with focus-trap and body-scroll-lock), the gallery state machine now spans three components, and the carousel's public shape widened. The defensive holes (effect-listener churn, captured-node ref, no out-of-bounds clamp) are not active bugs but each is the kind of subtle regression a refactor in this area would hit.
