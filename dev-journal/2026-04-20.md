## Session 1

Fixed a 500 on `/api/feed/:section` and cleaned up three `unstable_cache` wrapper-per-call anti-patterns in `legacySlug.ts`, `posts.ts`, and `projects.ts`.

### Decisions

- **Normalize `updatedAt` to ISO string inside the feed's cached fn** — picked over reparsing at each call site. Rationale: the cache contract becomes "strings in, strings out", the handler never has to care whether it read a fresh Date or a JSON-round-tripped string. One conversion site instead of two.
- **Lift `lookupLegacySlug`'s wrapper to module scope, drop per-slug tag** — the `legacy-redirect-${slug}` tag was declared but never revalidated anywhere in the codebase (grep-confirmed). Using `slug` as a function argument lets one module-level wrapper serve every slug.
- **Map-memoized wrappers for `getPostBySlug` / `getProjectBySlug`** — picked over either lifting with args (like legacySlug) or coarsening to the shared `"projects"` tag. Rationale: the per-slug tags in `projects.ts` **are** revalidated by admin routes on edit/delete (`src/app/api/admin/projects/[id]/route.ts`, `src/app/api/admin/projects/route.ts`), so targeted invalidation must be preserved. Map<slug, wrapper> keeps one wrapper per distinct slug, built lazily and reused. Applied the same shape to `getPostBySlug` for consistency even though its per-slug tag is currently unused (section-level tags do the invalidation work today).

### Tradeoffs

- **Memoization `Map`s never evict** — traded bounded memory for simplicity. Reversibility: easy (swap for LRU if it ever matters); see watch-out.

### Incidents / Bugs

- **500 on `/api/feed/tech`: `TypeError: Cannot read properties of undefined (reading 'getTime')`** — root cause: `unstable_cache` uses JSON serialization, which turns Prisma `DateTime` fields into strings on cache hits. `post.updatedAt.getTime()` (line 82) and `post.updatedAt.toISOString()` (line 90) both exploded when reading a cached result. Fix: normalize `updatedAt` to ISO string inside the cached function; adjust downstream sites to treat it as a string. `post.datetime` was unaffected (already a string in the schema, custom `yyyy-MM-dd-HHmm` format). Regression risk low — behavior on fresh fetches unchanged; cache hits now match the fresh shape.
- **Revalidation log spam showing cached function body as the key** — root cause: `unstable_cache(...)` was being instantiated inside `lookupLegacySlug` on every call, then immediately invoked. Next.js still routed to the right cache entry via `keyParts`, so the cache technically worked, but the wrapper-per-call tripped Next's "new cache registered" bookkeeping and printed the function source as the identifier. Fix: lift wrapper to module scope. Same anti-pattern found and fixed in `getPostBySlug` and `getProjectBySlug` (via Map memoization).

### What did I, Claude Code, or my agents learn from this

- **`unstable_cache` JSON-serializes its return value** — any `Date`, `Map`, `Set`, `BigInt`, etc. comes back as a string or mangled on cache hits. Normalize to serializable shapes (ISO strings, plain objects) **inside** the cached function so the handler has a single contract. The bug is invisible on fresh fetches and only surfaces under cache-hit conditions, which makes it a classic "works locally, 500s in prod after first revalidation" trap.
- **`unstable_cache(fn, keyParts, options)` returns a wrapper meant to be built once and reused.** Rebuilding it per call is wasteful, and Next logs each new wrapper as a revalidation event with the function body as the identifier — which is what the user saw and correctly flagged as "that doesn't look right." Two correct patterns: (a) lift to module scope and pass variable inputs as function arguments (keyParts can be a static namespace), or (b) Map-memoize wrappers keyed by the variable input when per-key options like tags are required.
- **When per-slug tags are declared but never revalidated, they're dead weight.** Grep for `revalidateTag(\`<prefix>-` before assuming a tag is load-bearing — dropping unused ones simplifies the caching shape.

## Session 2

### Decisions

- **`stripMarkdown` via AST walk, not regex** — used `unified` + `remark-parse` + `remark-gfm` (already in dep graph) to parse into an mdast and extract text node values. Regex alternatives considered but rejected as fragile for nested markdown. Fenced code blocks skipped entirely (noisy in excerpts); inline code kept (often meaningful).
- **Block node trailing `\n` for paragraph separation** — `paragraph`, `heading`, `blockquote`, `listItem` nodes get a trailing `\n` appended so sibling blocks don't run together after join. The final `replace(/\s+/g, " ").trim()` collapses all whitespace to single spaces. Alternative of joining children with `"\n"` at root level only was rejected as it wouldn't handle nested block structures.
- **`textOnlyProcessor` as a module-level constant** — consistent with the existing `markdownProcessor` pattern; avoids rebuilding the processor per call.

### Tradeoffs

- **AST walk over `strip-markdown` package** — no new dependency, reuses existing stack; cost is a local `MdastNode` type and `extractText` helper (~15 lines). Reversibility: easy to swap for `strip-markdown` if edge cases surface.

### What did I, Claude Code, or my agents learn from this

- **`unified().parse()` is synchronous** — only `.run()` is async. The parse step (mdast production) can be used in sync contexts, which means `stripMarkdown` doesn't need to be async despite living in the same file as `markdownToReact`.
- **Block vs inline distinction matters for text extraction** — without marking block nodes, sibling paragraphs run together (`"First.Second."`). Adding a trailing `\n` to block node output and normalising with `\s+` is the minimal fix.
