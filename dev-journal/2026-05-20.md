## Session 1

### Decisions

- **Replace `Project.platform: String` with `bucket: PlatformBucket` + `platformTags: PlatformTag[]`** — chose structured storage over keeping free-text with smarter parsing. Rationale: the old system had three separate derivation algorithms (regex word-boundary keyword matching for buckets, comma-split + set membership for display, prefix/substring + case-normalize for redundancy) all reverse-engineering structure from prose. Storage now matches editorial intent; picker no longer reverse-parses its own output.
- **Bucket as Postgres enum, not entity table** — gained exhaustive switch, type safety, and convention parity with the existing `Section` enum. Rejected the entity-table version because (a) the user has added zero buckets in the project's lifetime so "inline-add from picker" was over-engineering, (b) splitting `Section` (enum) and `PlatformBucket` (entity) for two similar editorial taxonomies is its own smell, (c) per-bucket display rules ("Fullstack" for Web) live cleanly in a `switch (bucket)` but require magic-string slug checks against an entity.
- **Tags also as Postgres enum (`PlatformTag[]`), not freeform `String[]`** — same enum-vs-entity rationale, plus tags-as-enum makes the canonicalization concern moot (the enum value IS canonical) and the Fullstack rule becomes pure enum equality instead of fuzzy string matching. Accepted that adding a tag is a schema migration; this is rare and editorial.
- **`bucket` is explicit editorial input, not derived from tag membership** — the prior system used keyword-order in `PLATFORM_BUCKETS` to route OSS-flavor web projects to the Open Source bucket via the `"Web"` tag. New picker has bucket as a separate radio; tags are honest descriptors. Open Source's suggested tags include every tag (since OSS spans platforms); other buckets are scoped to their natural sets.
- **Single project entry for multi-platform-multi-stack apps, primary bucket only** — the user has exactly one such project (mobile-led with fe+be counterpart). Chose single entry with primary bucket (iOS) + tags spanning the full stack, over two entries or a `secondaryBuckets` schema field. Rejected the secondary-buckets affordance: designing for n=1 is over-engineering and gallery-filter discoverability matters less at portfolio scale (~20 projects).
- **Compact-label rules in `compactLabel(bucket, tags)`** — 0 tags → bucket label; 1 tag → tag label; Web + Frontend + Backend → "Fullstack"; multi-tag all within bucket's natural set → bucket label; otherwise "Multiplatform". Extrapolated the natural-set fallback from the user's explicit "iOS + iPad → 'iOS'" guidance. Detail page renders `tags.join(" + ")` directly, no inference.
- **Skipped the disposable `/admin/migrate-buckets` review page on prod** — built it in phase 1, but the backfill produced clean data after one tweak (mapping the legacy `"Web"` tag → `[Frontend, Backend]` for the single OSS-Web project). User went straight from phase 1 to phase 2.
- **Two-phase deployment, with brief broken window accepted** — phase 1 (additive schema + backfill, deployed) → phase 2 (final schema + code rewrite, single commit). User explicitly accepted minutes of broken state between the `db:push` finalize and the code deploy.

### Tradeoffs

- **Enum-locked bucket vs entity-table bucket** — gained type safety, exhaustive switch, ergonomic display-label maps. Accepted that adding a 5th bucket requires `schema.prisma` edit + `db:push` + redeploy (~10 min). Reversibility: moderate — migrating enum → entity later is a one-time copy/swap dance, not exotic but not free.
- **Enum-locked tags vs freeform `String[]`** — gained type safety + canonical-by-construction + no typo-shadow taxonomy. Accepted that adding a tag is a schema migration even if it only describes one project. Reversibility: moderate — same enum → string-array migration if needed.
- **Single-entry-with-tags vs multi-bucket placement for cross-stack projects** — gained simplicity, no double-counting in the gallery. Accepted that the project is "invisible" when scrolling the non-primary bucket section. Reversibility: easy — add a `secondaryBuckets: PlatformBucket[]` field later if discoverability ever matters.
- **`compactLabel` returns bucket label for in-family multi-tags (e.g. [React, Next] → "Web")** — gained consistency with the user's explicit "iOS + iPad → iOS" guidance and a simpler mental model (all-natural collapses, anything outside-family triggers Multiplatform). Old logic returned "Multiplatform" for `"React, Next"`. Reversibility: easy — flip one branch in `compactLabel` if undesired.

### What did I, Claude Code, or my agents learn from this

- **Free-text DB column + multiple derivation algorithms is a strong, recurring smell** — when three different consumers (grouping, display, redundancy) each reverse-engineer structure from the same prose with different algorithms, the storage shape is wrong. If a picker has to reverse-parse its own output to render its UI, that's the signal.
- **Postgres enum arrays work natively with Prisma** — `PlatformTag[]` typed and indexable. No join table needed for descriptive tags that carry no extra attributes (no per-tag sort order, no relations). A join table would have been over-engineered here.
- **Identifier ≠ display label** — Postgres enum identifiers can't have spaces, so `MenuBar` (identifier) ↔ `"Menu bar"` (label) lives in a small `TAG_LABELS: Record<PlatformTag, string>` map. Same pattern as `BUCKET_LABELS` for `OpenSource` → `"Open Source"`. Don't fight Postgres' identifier rules.
- **Migration-window code can target the final schema** — during phase 2, every consumer was rewritten against the final schema shape (non-null `bucket`, no `platform`) even though the live Prisma client still reflected the intermediate state. Persistent stale-client diagnostics all clear together when the user runs `db:push` at the end. Better than a half-migrated codebase carrying transitional nullability.
- **Disposable migration UIs are sometimes worth building and then skipping** — built the `/admin/migrate-buckets` review page expecting the user to need it; backfill came out clean enough that they didn't. Time wasn't wasted — having it available as a safety net let them deploy with confidence. Pattern: build the safety net, plan to delete it.
- **`vi.mock` factories can close over top-level identifiers declared below them** — `vi.mock("…", () => ({ default: MockPlatformPicker }))` works even though `MockPlatformPicker` is declared after `vi.mock` in source order. Vitest invokes the factory at module-import time (post-hoist), so top-level bindings are in scope. Useful for keeping mocked React components named (rules-of-hooks).
- **Don't over-engineer for n=1** — the user's "multi-multiplatform" case is exactly one project. Designing a `secondaryBuckets` schema field for that one project would have added complexity (gallery double-counting decisions, picker UX for multi-select buckets) without payoff. Resist the pull toward symmetric flexibility when the data doesn't demand it.
