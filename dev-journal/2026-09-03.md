## Watch-outs & Tech Debt

Remove it and the route freezes on first render, pinning both the post body and the live-yet verdict — so the preview would keep serving after the post went live instead of redirecting. ## Session 1

### Decisions

- **A separate route, not `?overrideSchedule` on the post page** — reading `searchParams` in `/blog/[section]/[slug]` opts the whole prerendered route into dynamic rendering, putting every blog hit on billed compute. Rejected the query param outright rather than reaching for a `has`-query rewrite in `next.config.ts` (which would have preserved the param at zero cost but added routing-layer surface for one person's occasional use).
- **The route is public** — no session gate. The URL itself is the override, so a preview link works for someone with no account. Reversed mid-session: it shipped session-gated first on a safe-default reading of an unanswered question, then came out.
- **307, not 308, on the live redirect** — once `datetime` passes, the preview URL redirects to the canonical post. A permanent redirect would be cached by the browser and break the URL for the next post scheduled at that slug.
- **`resolvePost` split into `resolvePostRow` + a narrowing wrapper** — one clock read and one `fetchPostRow` cache entry still back both, but the teaser narrowing (title/date, never the body) is now a visible step rather than baked into the resolver. `PostRowResolution` carries the full row on both branches; only the preview route reads it.
- **No preview banner** — `PostContent` already renders the post's date under the title, so a future date is the signal. (Roland's call; the first draft had a banner.)
- **Route appended to the post path** rather than a top-level `/override-preview/:section/:slug`, since the starting point is always a post URL you're already looking at.
- **No `BlogPosting` JSON-LD, and `noindex, nofollow`** — the structured data asserts a published article at a canonical URL, and neither holds. No `robots.txt` `Disallow`: that would stop a crawler reading the `noindex` it needs to obey.

### Tradeoffs

- **Public URL means the convention is the secret** — anyone who learns the `/override-preview` suffix can read *any* scheduled post, not just one they were sent. Accepted deliberately; the escape hatch if it's ever abused is to require a search param on top. Reversibility: easy.
- **Scope held to the detail route** — list, archive, search, feed, `llms.txt`, sitemap and the `.md` twin all still filter scheduled posts out, so a post is never surfaced early to someone who didn't ask for this exact URL. Cost: no way to preview how a scheduled post will look *in a list*. Reversibility: easy.

### What did I, Claude Code, or my agents learn from this

- **Mutation-test the guard, not just the suite** — ran both load-bearing tests against a deliberately broken implementation (auth check inverted, then the `live` status compared against a bogus value) and confirmed each goes red. The project's own recurring lesson ("an untested guard is an unverified guard") applies to brand-new tests too, not only inherited ones.
- **A comment's justification can go stale faster than its code** — removing the session check turned `force-dynamic` from a precaution into a requirement without changing the line itself. Three docblocks still claimed a session gate and had to be rewritten. When a decision is reversed, grep for the prose that argued the old one.
- **Answer the question that was asked before the one that seems bigger** — the access question (auth vs public) was posed as load-bearing and got dodged in favour of the route shape; I filled it with a safe default instead of re-asking, and the work was thrown away when the real answer arrived one message later.

### Notes

- `verifySession()` was the right primitive for the discarded gated version, not `requireAdminPageSession` — the latter logs a middleware-bypass security event, and an anonymous hit on a route deliberately outside the `src/proxy.ts` matcher is an ordinary public request, not a bypass. Logging it as one would poison that signal.
- The new route is registered in `ROUTES_REQUIRING_REAL_404` in `src/app/loadingBoundaries.test.ts`: it 404s unknown slugs *and* carries two `redirect()`s, both of which a `loading.tsx` above it would degrade.
- Drafts (`published: false`) still 404 here — `fetchPostRow` filters at the query boundary before the datetime comparison runs, so this overrides the schedule and nothing else. Pinned by a test.
