## Session 1

### Decisions

- **Cron schedule → daily (`0 0 * * *`)** — chose daily over every-5-day (`0 0 */5 * *`). Rationale: removes future risk if Upstash tightens its idle threshold; cost is one trivial SET/day. Previous `0 0 1,11,21 * *` had 10-day gaps that exceed Upstash's ~7-day free-tier idle window — the root cause of recurring inactivity emails. History: started at `1,15` (15-day), tightened to `1,11,21` (10-day), now daily.
- **HMAC-pseudonymize IPs (not plain SHA-256)** — chose `HMAC-SHA256(IP_HASH_SECRET, ip)` truncated to 22 base64url chars. Plain SHA-256 is one-way mathematically but reversible in practice: IPv4 keyspace is ~4B, brute-forceable on a laptop in minutes. HMAC with a server-held secret blocks the rainbow-table shortcut.
- **Fail-open when `IP_HASH_SECRET` is missing on a Redis-configured deploy** — chose to disable rate-limiting (with warn at module load) over falling back to plain-IP keys. Rationale: regressing to plain IP would silently undo the GDPR posture improvement; admin lockout from a config gap is the only other failure mode and matches the existing no-Redis fail-open pattern.
- **No env var for `KEEPALIVE_KEY`** — chose hardcoded constant in `src/lib/keepalive.ts`. Rationale: zero operational value to making it configurable; an env-driven key is a future foot-gun ("which env had the old key?"). Centralized so cron and admin endpoints can't drift.
- **Manual admin trigger as a parallel endpoint, not bearer-shared cron** — chose `POST /api/admin/keepalive` (session-gated by `proxy.ts`) over expanding the cron's auth check to accept sessions. Rationale: keeps each route's auth concern single-purpose; KEEPALIVE_KEY is the only shared surface.
- **`prefetch={false}` only on per-row edit links** — kept default prefetch on `New post`/`New project` (cheap blank-form RSC) and tab links. Rationale: per-row edit-link prefetches were the actual DB-hit source on dashboard load; top-of-nav links don't query.

### Tradeoffs

- **Daily cron vs sparser schedule** — gained robustness to future Upstash policy shifts, accepted ~30 extra SETs/month (negligible); reversibility: easy (`vercel.json` one-liner).
- **Prefetch off on edit links** — gained: dashboard load no longer triggers N parallel RSC fetches with N Prisma queries; accepted: brief loading state on click instead of warm cache; reversibility: easy.
- **Helper extraction for keepalive** — only the constant moved to `src/lib/keepalive.ts`, not a full `runKeepalive()` function. Each route keeps its own Redis client + try/catch (5-line block). Avoids premature abstraction at the cost of allowing the two SET sites to drift on logging/error-shape; the constant is the only thing that must not desync. Reversibility: easy.
- **HMAC truncation to 22 chars (132 bits)** — kept full collision resistance for bucket purposes (132 bits is plenty for ~1 admin's worth of IPs); accepted: shorter audit-log strings; reversibility: trivial (change `.slice(22)` value).

But Hobby crons themselves can be auto-paused after project inactivity — distinct failure mode from Upstash idle detection.
- **Upstash idle detector excludes `PING`** — already documented in `route.ts` comment, but worth surfacing: any keepalive must use a real data command. SET of an observable key (`keepalive:last`) doubles as a "last successful run" marker visible in the data browser.
- **`@upstash/ratelimit` handles TTL automatically** — `PEXPIRE currentKey, window*2+1000` in [`node_modules/@upstash/ratelimit/dist/index.mjs:246`](node_modules/@upstash/ratelimit/dist/index.mjs:246). HMAC with a server-held secret blocks that for anyone *without* the secret — Upstash, exported logs, a Redis breach — which is the threat model that matters here. - **App Router `<Link>` prefetches on viewport entry, not just hover** — a list of N edit links on a dashboard fires N background RSC fetches, each running its target page's server code. `prefetch={false}` per-link is the lever; there's no global "no prefetch on list pages" setting.

## Session 2

### Decisions

- **Time-based scheduled publishing without cron** — switched from "cache captures `now` at fill time" to "cache stores rows regardless of datetime; filter `datetime <= now` applied at read time." A post with a published flag and a future `datetime` auto-surfaces the first request after the boundary, no cache bust required. Granularity is request-driven, not minute-accurate; fine for a blog. Alternatives rejected: (a) Vercel Cron hitting a revalidate endpoint — overkill for personal blog; (b) dropping caches entirely and relying on request-time freshness — gives up the cache benefits across all reads, not just the time-boundary case.
- **Padded bounded caches over a single full-list cache** — for paginated reads (page 1 of section list, feed), the cache fills with `LIMIT + futureCount` rows so the read-time filter can strip futures and still slice a full page. Alternative considered: cache the entire published list and filter+paginate post-cache. Padding wins because: cache stays bounded by PAGE_SIZE in the common case (futureCount=0), with extra rows only when scheduled posts exist; no extra DB query per request. The "cache + backfill query when futures leak" variant I sketched first was strictly worse (extra request-time DB hit) and the user steered me to the cache-time pad.
- **`totalPages` moved to request-time count** — previously cached inside the page 1 fetcher (so the count captured `now` along with the rows). Now a separate `prisma.post.count({ where: publishedWhere })` runs on every page 1 request. Reason: a cached count stays stale as futures cross their date, and "last page is N but really N+1" leaves posts unreachable. Cost: one indexed count query per cached page 1 request. Trivial.
- **Unbounded caches (archive, sitemap-slugs) just drop the filter** — these caches already hold the entire published list per section / globally; no padding needed. Read-time wrapper applies the `datetime <= now` filter and (for archive) regroups by year. Same self-surfacing behavior.
- **Single-row caches (`getPostBySlug`, `legacySlug`) filter at the wrapper boundary** — cached row carries `datetime`; the wrapper returns `null` if `datetime > now`. Legacy-slug cache now stores `datetime` too (one extra field per match).

### Tradeoffs

- **Page 1 / feed cache holds `LIMIT + futureCount@fillTime` rows until tag-bust** — once all futures cross their date, the originally-live rows at the tail of the padded window become dead weight (still cached, never sliced). Worst case: bulk-schedule 20 posts then never write again → ~20 extra `PostListItem` rows per section (≈100KB) sit in cache indefinitely. First mutation rebuilds the cache and clears the bloat. Reversibility: easy — add `revalidate: <seconds>` to the bounded caches to auto-refill periodically. User declined for now; "recache" admin button is the alternative if the bloat ever matters.
- **Feed pre-renders markdown for scheduled posts that get filtered out at read time** — small wasted compute at cache fill, in exchange for keeping the cache shape simple (no two-stage "filter then render" inside the GET handler).
- **Read-time filter matches PostgreSQL string compare for malformed datetimes** — both reject lex-`>` strings as "future." Previously the DB filter did this server-side, the JS filter now does the same client-side. Identical real-world behavior; only the test mocks were affected (see Incidents).

They passed only because the mocked `prisma.post.findMany` ignored the where-clause — in real Postgres those rows would have been filtered out by `datetime <= now` and never reached the renderer. ### What did I, Claude Code, or my agents learn from this

- **Caches that "capture `now`" can quietly break time-based features** — the original code captured `currentDatetimeString()` inside every `unstable_cache` factory so future-dated posts were forever invisible until a mutation fired. Reads looked correct because `now` was always whatever it was at fill time. The fix is to push the time-dependent comparison *out* of the cached function and into the wrapper that reads from it; the cache becomes time-independent and the wrapper handles fresh `now` per request.
- **Don't trust a test that passes because the mock skipped a filter** — the `"not-a-date"` fallback tests passed for years but were unreachable in production. When refactoring a filter from DB-side to JS-side, audit tests that depend on the filter being a no-op.
- **For paginated caches with a "must return N items" contract, padding at fill time beats backfilling at read time** — the conversation walked through both options. Padding (`take: LIMIT + futureCount`) is one extra count query at fill time and zero extra at read; backfilling is zero at fill and a conditional extra query at every read when futures exist. For caches that fill rarely and read often, padding wins.
