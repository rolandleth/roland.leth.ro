## Session 1

### Decisions

- **`slug:` frontmatter is the slug source of truth** — chose an explicit, self-healing field over re-deriving the slug from the title on every import. Title-derivation silently moves a legacy or retitled post's URL; an authoritative `slug:` can't. The importer resolves via `resolveSlug` = `createSlug(fileSlug ?? title)` and writes the resolved value back into the file (`setFrontmatterSlug`), so the content repo converges to fully-explicit slugs.
- **`createSlug` idempotency doubles as the canonical-shape check** — a well-formed slug passes through `createSlug` unchanged, so one comparison (`fileSlug === slug`) distinguishes "explicit & valid" (use verbatim, no rewrite), "non-canonical" (normalize from the value itself, rewrite), and "absent" (derive from title, rewrite). Avoided a separate slug-validator.
- **Malformed `slug:` self-heals from its own value, not the title** — `createSlug("My Cool Slug")` → `my-cool-slug`, preserving author intent, rather than falling back to the title. Empty normalization skips with a distinct reason.
- **`.md` export emits `slug:`** — `buildPostMarkdownFile` now carries `slug: <post.slug>` so an export→import round-trip lands on the same DB row even when the stored slug diverges from what the title would derive. One line closes a duplicate-post hole.
- **`init-post-slugs.ts` matches files to DB rows by filename datetime, title fallback** — chose the datetime (the import contract's stable key; overwrites refresh DB datetime from the filename) with an exact-title fallback over title-only matching. Zero/ambiguous matches are reported and left untouched, never guessed; script exits non-zero so a partial init can't pass for complete.
- **Kept `init-post-slugs.ts` as a resync tool** — chose to keep over delete-after-one-run. It doubles as a DB→files slug resync after a restore or DB-side correction; idempotent (correct files count as "already correct"). Header and `simplified:` comment reworded away from "THROWAWAY".
- **`prepareBatch` (admin bulk route) delegates to `parsePostFiles`** — chose to share the importer's parse/gate pipeline over keeping the route's copy-adapted ~60-line gate loop. Removes the drift risk that copy introduced (route had reverted to `createSlug(title)`, ignoring `slug:`). `resolveSlug` returned to private since the sharing moved up a level.

### Tradeoffs

- **Shared `parsePostFiles` between script and route** — gained a single answer to "which files import, under what slug"; accepted that the route now imports from `@/lib/import/postImport` and drops the returned `slugRewrite` (an upload can't be written back). Reversibility: easy.

### What did I, Claude Code, or my agents learn from this

- **Idempotent normalizers make good validators** — when a canonicalizer is idempotent, `x === normalize(x)` is a free "is-canonical" predicate; no separate validation branch needed. This collapsed three slug cases into one comparison.
- **Copy-adapting a gate pipeline invites drift** — the admin bulk route had been hand-copied from `parsePostFiles` in a prior session; when the slug rule changed, only the script got it and the route silently diverged (re-derived from title). Sharing the pipeline removed the class of bug, and the existing route tests passing unchanged confirmed behavior was preserved.
- **Fix the starting data, keep the rules** — after `init-post-slugs.ts` set correct slugs, the instinct was to question whether the import/admin logic was still needed. It is: the init fixed the *data*, the logic enforces the *invariant* for every post written afterward. Data migration and rule enforcement are separate concerns.
