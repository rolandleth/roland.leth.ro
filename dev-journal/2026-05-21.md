# Dev Journal – 2026-05-21

## Open Threads

## Watch-outs & Tech Debt

- **PUT route `...rest` spread is still load-bearing** — `src/app/api/admin/projects/[id]/route.ts` spreads `projectUpdateSchema.partial()` output straight into Prisma's `update`. The schema-level `superRefine` added today only catches bucket/tag *coherence* (when both fields are present in the same payload). A future field whose Zod name diverges from the Prisma column still gets silently lost. Same trigger as 2026-05-20: revisit when adding such a field.
- **Coherence superRefine can't validate update PUTs that change only one of bucket/tags** — the schema returns early when only one is present (it can't know the persisted value). If a future field-rename or migration introduces a window where rows have an old bucket and the admin patches only tags, the API will accept a now-incoherent payload. Trigger: any structural migration to `Project.bucket` or `Project.platformTags`. Mitigation if hit: re-validate after read-modify-write inside the PUT txn, or send both fields together.

## Session 1

### Decisions

- **Run today's code review automatically, then fix what still applies** — the scheduled daily-code-review task surfaced 10 findings across the 2026-05-20 platform refactor. Walked the list against current code, dropped 6 as false positives (single-tag branch fires before Fullstack, `gallerySelect` already extracted, discontinued styling intentional with WCAG-AA comment, POST/PUT reorder isn't real duplication, Serializable retry is journal-deferred, OpenSource catch-all already commented). Acted on the remaining four themes: schema gates, picker UX, db helper split, gallery perf.
- **Single `superRefine` for bucket/tag coherence, shared across create + update** — built create/update from a common `projectFields` map so `.partial()` still works on the update side. Alternative (duplicate the refine inline per schema) rejected — keeping the rule in one function means a tag rename or a new bucket can't drift between create- and update-side validation.
- **Schema-side coherence uses `BUCKET_SUGGESTED_TAGS`, not `BUCKET_NATURAL_TAGS`** — picker offers every tag for OpenSource by design (an OSS iOS library is valid). Schema mirrors what the picker can produce; anything outside is rejected. Using `NATURAL` would have wrongly rejected `[Library, iOS]` on OpenSource.
- **Coherence check only fires when both bucket and platformTags are present in the same payload** — PUT semantics: changing only tags leaves the persisted bucket as-is; the schema can't validate against state it doesn't see. Documented as a watch-out (above). Alternative (always require both on PUT) rejected as it would force the admin form to send unchanged fields just to satisfy validation.
- **Drop the picker's hidden `required readOnly` sr-only input; gate on the form's submit handler instead** — the hidden-input pattern was load-bearing for "won't submit if empty," but browser-tooltip target was invisible, screen readers got nothing, and the synthetic value (`${bucket}:${tags.join(",")}`) had a "null:" edge case. Surface through the existing `<ErrorMessage>` slot instead; that's the path the rest of the form already uses.
- **Removed the `state.bucket as PlatformBucket` cast** — the cast was "safe" only because of the hidden input it depended on. The new explicit submit-handler guard narrows `state.bucket` from `null` to `PlatformBucket` via an early-return pattern, so the cast is gone and the form/picker contract is no longer invisible.
- **Pruned-tag hint surfaces in the picker, not the form** — when a bucket switch drops tags incompatible with the new bucket, render a transient `role="status" aria-live="polite"` message ("Removed N tag(s) not valid for this bucket"). Auto-clears on any tag chip interaction. Internal state, not a prop — UI-only feedback that the parent doesn't need to know about. Rejected: passing prune info up through `onChange` (parent doesn't act on it; would just plumb state through two layers for no payoff).
- **Split `getAllProjectsForGallery({ sortDiscontinued })` into two named functions** — `getProjectsGalleryCached()` (public, cached, discontinued-last) and `getProjectsForAdmin()` (admin, uncached, sortOrder+name). One boolean controlling both cache use AND ordering coupled two orthogonal concerns; the split makes the cache contract local to its function and removes the "wrong flag → wrong cache" footgun.
- **Reused for-of loop pattern for the projects/page partition** — single pass over `allProjects` partitions featured/others AND precomputes `showPlatformCapsule` per non-featured project. Matched the existing `groupsWithStaggerStart` pattern (the file already documents why `.reduce`/`.map` with a mutated accumulator trips the React Compiler's immutability rule).
- **Featured cards still always show the platform pill (didn't mirror Compact's redundancy check)** — explicitly skipped per the plan: featured emphasis outranks consistency with grouped cards. The pill is a deliberate visual repeat in the featured row, not redundancy.

### Tradeoffs

- **`superRefine` on the parent object means create/update can't be further `.partial()`'d** — the resulting schema is a `ZodEffects`, not a `ZodObject`, so any downstream `.partial()` would fail. Acceptable because we only call `.partial()` once at construction time. Reversibility: easy (refactor to manual `.optional()` on the field map if a future consumer needs another partial layer).
- **Coherence check skipped when only one of bucket/tags is present** — gains: PUT semantics work as expected (you can patch tags without resending the bucket). Accepts: a maliciously-crafted PUT that changes only `platformTags` could land tags that no longer fit the persisted bucket, until the next full edit. Reversibility: moderate — could mitigate by reading the row first and combining persisted + payload values inside the route, but that adds an extra round-trip per PUT.
- **`MockPlatformPicker` in `ProjectForm.test.tsx` exposes a mutable `mockPickerConfig.autoFillEnabled` toggle** — gains: a single test exercises the empty-picker validation path that the auto-fill mock previously masked. Accepts: tests now share a module-level holder; reset in `beforeEach` is mandatory. Reversibility: easy — splitting into two mock variants and `vi.doMock`'ing per test would clean it up, but it's overkill for one branch.
- **The `superRefine` builds a frozen `BUCKET_SUGGESTED_SETS` (one Set per bucket) at module load instead of rebuilding on each parse** — gains: avoids reallocating 4 Sets per project create/update. Accepts: the static map duplicates what `BUCKET_SUGGESTED_TAGS` already conveys as arrays. Trivial cost; declaration is local to `schemas.ts`.

### What did I, Claude Code, or my agents learn from this

- **Zod 4's `.partial()` keeps inner field validations alive when a value is present** — a `.partial()` schema with `platformTags: z.array(...).min(1)` rejects `platformTags: []` and accepts `platformTags: undefined`. Inner refines/min/max only short-circuit on `undefined`. The analyzer's worry that PUT was silently accepting empty arrays was wrong; pinned with a test before changing the schema.
- **Verify analyzer findings against current code before fixing** — of the original 10 issues, only 4 themes were real; 6 were false positives the analyzer (working from gathered evidence summaries, not the file) couldn't see were already addressed inline or were intentional design choices documented in comments. Pattern: read the cited file, including comments, before treating any finding as actionable.
- **The React Compiler's `immutability` rule fires on `let` mutations captured inside `.map`/`.reduce`** — the projects/page already documented this; matching the existing for-of pattern in the new single-pass partition was safer than introducing a `reduce` that would have tripped the same rule.
- **`prefer-const` ESLint autofix runs on test files via the post-edit hook** — declaring `let mockAutoFillEnabled` got rewritten to `const`. Workaround: use a holder object (`const mockPickerConfig = { autoFillEnabled: true }`) so per-test mutation doesn't trip the rule.
- **`Object.fromEntries` widens its return type** — the initial attempt `const X: Record<PlatformBucket, ReadonlySet<PlatformTag>> = Object.fromEntries(...)` failed because TS can't narrow `[string, T][]` back into a discriminated `Record<EnumUnion, T>` without `as unknown as ...`. Manual literal `{ iOS: new Set(...), Mac: new Set(...), ... }` is cleaner and type-checks naturally.
