## Session 1

### Decisions

- **Post summary becomes a required, auto-derived field** — flipped `Post.summary` from `String?` → `String NOT NULL` in `prisma/schema.prisma`, with a write-time invariant that summary is never empty. Auto-derive runs on create (when blank), on bulk import (always — no input mechanism), and on edit (when the field was cleared OR when body changed AND the user hadn't authored a new summary). Alternative considered: parse YAML frontmatter in bulk-imported files to mirror "user provides it" from the single-post form. Rejected — the only client input is a file picker, so frontmatter would have been the only carrier, and auto-derive covers the same gap without adding a new file format or a `gray-matter` dependency.
- **Summary cap tightened from 300 → 160 chars** — matches Google's desktop snippet display width (~155–160). Old 300 was wishful; the consumers (OG meta description, Atom `<summary>`) truncate beyond ~160 anyway. Schema, derivation, and the old feed fallback constant `FEED_SUMMARY_MAX_CHARS` all collapse to one number: `SUMMARY_MAX_CHARS = 160` in `src/lib/markdown.ts`. Project `summary` cap stays at 300 — different consumer (project page hero text), not in scope.
- **Cleared-on-edit re-derives, even if user "intentionally" cleared** — the form sends `summary: state.summary || undefined`, so cleared and untouched-when-empty both arrive as `undefined`. Rather than try to distinguish them (which the form can't preserve without a new field), the route treats any empty submission as "give me a fresh auto-derive." Keeps the "never empty" invariant honest and removes the need for client-side state to disambiguate.
- **Edit-route compare logic lives inside the existing Serializable transaction** — added `body` + `summary` to the `findUnique` select so the resolution sees the pre-update state as-of the txn snapshot, not a separate read. Rules: authored (`summary != previous.summary`) → keep; untouched + body changed → re-derive; cleared → re-derive; untouched + body unchanged → skip the column (Prisma treats `undefined` as no-op so no write amplification).
- **Read-time fallbacks deleted, not kept as defensive null-guards** — once the column is NOT NULL the generated TS type is `string`, so `post.summary ?? undefined` in blog metadata and `post.summary ?? stripMarkdown(...)` in the feed become genuinely dead. Leaving them as "safety nets" would mean code that can never run; deleted both, plus the `FEED_SUMMARY_MAX_CHARS` constant. The whole point of the migration was to lean on the type system.

### Tradeoffs

- **Word-boundary truncation with hard-slice fallback** — `deriveSummary` strips markdown via `stripMarkdown`, takes the first 160 chars, walks back to the last whitespace, appends `…`. If the stripped text has no whitespace at all within 160 chars (URL-like blob), falls back to a hard slice so callers always get a bounded string. Cost: a single linear scan; benefit: no mid-word `implementati…` artefacts in search snippets. Reversibility: easy — single helper.
- **Bulk import always derives, ignoring any author intent** — the filename grammar only encodes datetime + title, so there's no per-file summary channel. Trade: bulk-imported posts can't carry an authored summary until the admin opens the edit form. Mitigation: the admin can refine via the per-post form after import. Reversibility: moderate — would require either frontmatter parsing or a new payload shape.
- **Edit-route schema gate triggers BEFORE the route's auto-derive logic** — `postUpdateSchema.summary.max(160)` rejects a 161-char user-supplied summary with a 400. That's intentional (don't let oversized strings reach the DB) but it does mean a sloppy paste from the admin form gets a hard rejection rather than a silent truncation. Reversibility: easy — flip to `.transform(s => s.slice(0, 160))` if the UX bites.

### Environment / Config Changes

- `prisma/schema.prisma`: `Post.summary` is now `String` (not `String?`). Prisma client auto-regenerated by a workspace hook on schema edit (no manual `prisma generate` needed). Requires `yarn db:push` (or a deploy migration) to apply the NOT NULL constraint to production — the user confirmed no rows currently have a null summary, so the migration is a no-op at the data level.

### What did I, Claude Code, or my agents learn from this

- **"By design" is a retcon trap** — when the user pushed back ("why was it implemented like this?"), I had to walk back the "by design" framing from the previous turn. The bulk import never set `summary` not because of a deliberate boundary, but because I never threaded the field through when building it. The honest answer was "I missed it." Lesson: when explaining why a current implementation behaves a certain way, separate "this was a considered choice" from "this is what happens to happen." Default to the second unless there's evidence (comment, test, PR thread) for the first.
- **A migration changes whether read-time fallbacks are dead** — initially called the feed's `?? stripMarkdown(...)` and metadata's `?? undefined` "dead" after auto-derive landed. User caught this: without flipping the column to NOT NULL, those branches are TS-required null guards even if they never fire at runtime. They only become genuinely deletable after the type narrows from `string | null` to `string`. Lesson: "in practice never fires" and "dead code" aren't the same thing — the type system is the authority on which branches the code is allowed to omit.
- **Schema-sync projects (`prisma db push`) don't have migration files to author** — when I went looking for `prisma/migrations/` and found nothing, the workflow is "edit schema.prisma → run `yarn db:push`." No SQL to write, no version-tracked migration. Worth remembering for future schema work in this repo.

## Session 2

### Decisions

- **userEvent perf via `setupUser()` helper** — created `src/test/user.ts` exporting `setupUser()` that returns `userEvent.setup({ delay: null })`. Default v14 typing schedules a `setTimeout(0)` per keystroke, which dominates input-heavy tests. Centralised so future user-event option tuning is one line. Rejected per-file inlining (DRY violation) and module-scope shared instance (state-bleed between tests).
- **Force `AnimatePresence` to `mode="sync"` in tests** via `vi.mock("framer-motion", ...)` in `src/test/setup.dom.ts`. Production keeps `mode="wait"` where set; the mock wraps the real component and overrides only the `mode` prop. Rejected: full-mock of `motion.*` (broke 4 form-submit-via-Enter tests — root-caused below), `MotionGlobalConfig.instantAnimations = true` (same breakage), `AnimatePresence` → `Fragment` (same breakage).
- **Mock `PlatformPicker` and `PresetOrFreeformInput` inside `ProjectForm.test.tsx`** — both have dedicated test files, so ProjectForm doesn't need to integration-test their internals. Mock fidelity: `PlatformPicker` → bare `<input aria-label="Platform">`; `PresetOrFreeformInput` → `<select id={id}>` rendering all `presets`. Dropped `required` from the select mock — initialData.role="Developer" isn't in presets, so a required select with value="" would block submit via HTML form validation in edit-mode tests.

### Tradeoffs

- **`mode="sync"` everywhere in tests** — tests no longer assert on the sequential exit→enter ordering of `mode="wait"`, but none did. Reversibility: easy (single mock site).
- **Stubbed `PlatformPicker`/`PresetOrFreeformInput` in ProjectForm tests** — gave ~2x on ProjectForm runtime, lost integration coverage of the form rendering the real picker/select sub-tree. Justified because both have their own dedicated test files. Reversibility: easy (delete the two `vi.mock` blocks).
- **Module-scope `const user = setupUser()` per file** — one user instance shared across all tests in a file rather than per-test. Matches existing pattern; risk is state-bleed (focused-element tracking) between tests in the same file. Hasn't manifested. Reversibility: trivial.

### Incidents / Bugs

- **happy-dom `<form>` Proxy identity bug — diagnosed, NOT fixed** — `formRef.current.contains(input)` returns `false` even when the input is structurally inside the form. Root cause: happy-dom wraps `HTMLFormElement` in a `Proxy` (constructor returns it), but `Node.prototype.parentNode` getter returns the raw internal node via `[PropertySymbol.parentNode]`. `NodeUtility.isInclusiveAncestor` then walks via the raw parentNode chain and compares strict-equal against the Proxy stored in the ref — they never match. `event.composedPath()` has the same issue (also uses the `.parentNode` getter, returns raw nodes). In production code (`useClickOutside.ts:21`), this would falsely fire `onOutside` during a `mousedown` on an element inside the form. Today it's masked: the 200ms `mode="wait"` exit animation keeps the form mounted long enough for the subsequent `keydown(Enter)` to fire `submit` before unmount. Forcing `mode="sync"` preserves the masking (form still has a 200ms exit window, just running parallel to the new child's enter). This is why removing animations entirely broke the 4 tests but switching to `mode="sync"` doesn't.

### Environment / Config Changes

- `src/test/setup.dom.ts`: added `vi.mock("framer-motion", ...)` forcing `AnimatePresence` `mode="sync"`. Production unchanged.
- `src/test/user.ts`: new file exposing `setupUser()`.
- 21 test files migrated from `await userEvent.X(...)` to `const user = setupUser()` + `await user.X(...)`.

### What did I, Claude Code, or my agents learn from this

- **Per-file vitest timings have ~30%+ noise** under parallel execution. Compared baseline-vs-after on a single file three times before drawing conclusions — initial 211ms→622ms→465ms→488ms spread for the same test made me chase ghosts. Use total `tests` time across the suite (or solo runs of a single file) as the signal, not single per-file numbers in the parallel reporter.
- **happy-dom's form Proxy quirk** is documented in source (`HTMLFormElement.js` line 38 — constructor returns a Proxy; `Node.js` line 256 — `contains()` has a comment about it). Any production code using `node.contains(target)` for click-outside detection against a `<form>` or `<select>` will misbehave under happy-dom tests *unless* something else (e.g. an animation delay) keeps the node alive past the spurious unmount.
- **`mode="wait"` cost in tests is twofold**: (a) sequential `exit + enter` = 2× wall-clock per swap, and (b) `findBy*` blocks until the *new* child mounts, which is `exit` wait + first poll interval. Switching to `sync` collapses both: total = `max(exit, enter)`, and new child mounts immediately. BlogSectionHeader went 1295ms → ~200ms from this alone.
- **`userEvent.setup({ delay: null })`** doesn't help framer-motion-bound tests (animations dominate, not keystrokes). It helps purely input-heavy tests (LoginForm, PostForm, ProjectForm) by maybe 30-50%.

### Notes

- Total `tests` time: 8.91s → 4.69s (~47% faster) over 79 test files. Wall-clock Duration: 5.59s → 4.31s.
- Per-file standouts: BlogSectionHeader 1295→~200ms, AdminSearch 747→~245ms, ExpandableSearch 597→~226ms, PostForm 404→~282ms, ProjectForm 1471→~560ms (~2.6x).
- The four originally-failing form-submit-via-Enter tests (`ExpandableSearch`: submits trimmed value; `AdminSearch` × 3) all pass under `mode="sync"` because the form still has a 200ms exit window during which `submit` can fire.
- `vi.unmock("framer-motion")` is the per-file escape hatch if a future test needs to assert on real `AnimatePresence mode="wait"` behaviour.

### What did I, Claude Code, or my agents learn from this

- **Bash cwd persists across tool calls. Period.** The system prompt says it explicitly. If the project's hooks reference relative paths (and many do — see `.claude/hooks/auto-allow.jq`), a `cd` into a subdir locks the session out of every tool until cwd is restored — and the very tool that would restore it is also blocked. Rule for next time: never `cd` for `git mv` / `mkdir` / etc. — always use absolute or repo-root-relative paths in the command itself (`git mv src/lib/db.ts src/lib/db/`).
- **Edit doesn't scale for mechanical bulk refactors.** 220 substitutions of identical shape (`"@/lib/X"` → `"@/lib/<bucket>/X"`) took ~10 turns of 20–30 parallel Edit calls each. The per-edit formatter + diagnostics noise dominated context and wall-clock. The right move when this shape appears: stop after 2–3 rounds and ask the user to approve a one-off `sed -i '' -f /tmp/script.sed <files>` — `~/.claude/rules/workflow.md` and the global CLAUDE.md explicitly contemplate this ("use Bash only when no dedicated/builtin tool covers it, and confirm with the user first; non-negotiable"). Going further is grinding for the sake of staying in-grammar.
- **LSP tool surface doesn't expose rename/move-file refactors** — `tsserver` itself supports `getEditsForFileRename` (the API behind "move file → auto-update imports"), but our `LSP` operation enum only has navigation (`goToDefinition`, `findReferences`, `hover`, symbol search, call hierarchy). If it exposed the rename op, the 220-import rewrite would have been a free side effect of `git mv`. Worth knowing for the next reorg.
- **Drafted sanctioned `sed -i '' -f` grammar for the project hook** (in Session 3 chat) — locked script path to `/tmp/rlr-<ident>.sed`, fenced target paths under `src/` with `.tsx?` extension and a negative lookahead forbidding `..`. Not committed; tracked as an Open Thread above.
