### Decisions

- **Hex-format check on `ADMIN_HASH_PASSWORD` only, not `SESSION_SECRET`** — schema enforces `^[0-9a-f]*$` on the bcrypt-hash field so misconfigured deploys fail loudly via `EnvConfigError` instead of silently decoding to garbage and producing 401s. `SESSION_SECRET` is consumed via `TextEncoder().encode()` (not `Buffer.from(..., "hex")`), so any string is valid — initial mistake was to add the regex there too based on a misleading CLAUDE.md note. Alternative (validate at consumer site) rejected as redundant and easier to forget.
- **Typed `EnvConfigError` over generic `Error`** — required-var failures throw `EnvConfigError` with `code: "ENV_MISSING"` and `varName` so middleware can branch on `instanceof`/`code` (matching the existing `jose` `error.code` pattern in `verifyToken`). Alternative (untyped `.code` property tag) rejected as less discoverable.
- **Module-load dummy bcrypt for null-credentials timing defense** — precompute `bcrypt.hashSync("dummy", 10)` at import time and run `bcrypt.compare(password, dummyHash)` when `getAdminCredentials()` returns null. Alternative (lazy/cached in a closure) rejected: paying ~80ms once at cold start is more predictable than a one-time slow request.
- **Pass resolved Redis config object to `new Redis({...})`** — both `login/route.ts` and `cron/ping/route.ts` now construct from the object returned by `getRedisConfig()` instead of calling `Redis.fromEnv()` (which re-reads `process.env` directly). Single source of truth: if env-var names ever drift in `env.ts`, the gate and the SDK can't desync.
- **`crypto.timingSafeEqual` via `isAuthorized` helper for cron Bearer** — extracted helper that runs a same-length dummy compare on length mismatch. Alternative (inline) rejected as it would obscure the dummy-compare-on-mismatch step.
- **Performance finding (#7) deliberately deferred** — chose to leave the per-call `safeParse(process.env)` as-is over (a) module-scope memoization or (b) hot-path direct `process.env` read. Rationale: protected-request cost is negligible, and (a) would break the doc-stated `vi.stubEnv` testability contract. Documented as a watch-out above.
- **Followed project's existing strikethrough resolution convention** in `code-reviews/2026-04-26.md` (per commit `8a33057`'s `~~**...**~~ — resolved.` pattern) rather than the `wrap-up` skill's `- [x] ... **Resolved**:` default. Consistency with prior practice over the skill default.
- **Class form for `Redis` mock in `cron/ping/route.test.ts`** — `class { ping = vi.fn().mockResolvedValue(...) }` over `vi.fn().mockImplementation(...)`. The latter doesn't behave as a constructor when called with `new`.

### Tradeoffs

- **Hex regex on `ADMIN_HASH_PASSWORD`** — gained loud schema-level failure on misconfigured deploys; accepted that future test fixtures must use hex values (one fixture rewrite was needed). Reversibility: easy.
- **Bearer length leak in cron `timingSafeEqual`** — gained constant-time byte comparison; the expected secret's length is now observably leaked via response timing on length mismatch. Acceptable for a server-configured secret; would need revisiting if the cron secret ever became user-controlled. Reversibility: easy.
- **Module-load dummy bcrypt** — gained timing-defense in the no-credentials path; accepted ~80ms one-time cold-start cost. Reversibility: easy.

### Incidents / Bugs

- **Initial misapplication of hex regex to `SESSION_SECRET`** — root cause: the CLAUDE.md env-vars block read "JWT signing secret (hex-encoded)", which I treated as a usage contract. Actual usage in `auth.ts:22` is `new TextEncoder().encode(getRawSessionSecret())` — bytes-of-string, not hex-decoded. Fix: reverted the regex on `SESSION_SECRET`, kept it on `ADMIN_HASH_PASSWORD` where it's actually `Buffer.from(..., "hex")`'d, and updated CLAUDE.md to "any string". Caught by user correction during the implement phase. Lesson recorded below.
- **`vi.fn().mockImplementation(() => instance)` not usable as constructor** — first attempt at the Redis mock returned the implementation directly when called with `new`, throwing `is not a constructor`. Fix: switched to a class literal mock. Test now exercises the actual `new Redis(redisConfig)` path.
- **Two pre-existing bugs surfaced and fixed** — `ProjectContent.tsx:77` was interpolating the nullable `accentColor` (not the `accent` fallback) into a `color-mix()` string, producing invalid CSS on projects with no accent. `ProjectForm.tsx` `Number(e.target.value)` produced `NaN` on partial-entry/cleared `sortOrder` inputs, sending `null` in the JSON payload and causing confusing Zod 400s.

### What did I, Claude Code, or my agents learn from this

- **Verify a format claim against the consumer site, not against a doc-comment.** When adding a schema validator (hex, URL, length) for an env var, grep its usages and check whether the consumer actually parses that format — `Buffer.from(..., "hex")` vs. `TextEncoder().encode()` is the kind of distinction that doc-comments routinely get wrong, and a misapplied regex narrows the valid input space without warning.
- **`vi.fn().mockImplementation(fn)` is not a constructor.** When mocking an ES class that the SUT instantiates with `new`, mock with a class literal (`class { method = vi.fn() }`) rather than `vi.fn().mockImplementation(() => instance)`. The latter throws `is not a constructor` because the impl runs as the body, not the prototype.
- **Resolution-marker convention in this project is strikethrough, not checkbox.** Future "mark resolved" passes should follow `~~**…**~~ — resolved. <how>` (per `code-reviews/codebase-2026-04-24.md` and commit `8a33057`), not the `wrap-up` skill's default `- [x] … **Resolved**:` format.
