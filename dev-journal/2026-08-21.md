## Session 3

### Decisions

- **Reduced motion handled globally, not per-caller** — new `src/components/MotionPreferences.tsx` wraps the app in Framer's `<MotionConfig reducedMotion="user">` from `src/app/layout.tsx`; `fadeUp` is unchanged apart from a docblock pointing at it. Rejected a `useFadeUp()` hook (would touch 7 call sites and still leave `ProjectFaq`'s chevron rotate + accordion height, `BlogSectionHeader`'s `y`, `ExpandableSearch`'s `x`, and `ThemeToggle`'s `layoutId` unprotected, and a future component can forget it) and a CSS `!important` override on a data-attribute (fights inline styles Framer rewrites every frame).
- **`initial` deliberately left alone** — the obvious hook shape returns `initial: false` under reduced motion. That is a hydration mismatch: Framer SSRs `initial` as inline style, the prerender can't know the preference, and `useReducedMotion()` reads `matchMedia` synchronously in the hook body so the client's *first* render already disagrees. `reducedMotion="user"` changes the transition, never the rendered `initial`.
- **jsx-a11y wired as rules-only, scoped to `**/*.tsx`** — spreading `jsxA11y.flatConfigs.recommended` fails at startup: `eslint-config-next` registers the plugin as a module-namespace object, the flat config registers the inner plugin object, and flat config rejects the second registration (`Cannot redefine plugin "jsx-a11y"`). Enabling the rule ids against next's existing registration sidesteps it.
- **Four of five jsx-a11y findings fixed in rule options, not source** — each landed on code that was more accessible than the rule's default assumption: `role="list"` on a `list-none` `<ol>` (the WebKit list-semantics workaround), `tabIndex={0}` on a scrollable `role="group"` container (WCAG 2.1.1), and `SearchForm`'s `autoFocus` *prop*, which is deliberately not forwarded to the input. Options set: `{ ol: ["list"], ul: ["list"] }`, `roles: ["tabpanel", "group"]`, `ignoreNonDOM: true`.
- **Lightbox backdrop gates on `event.target === event.currentTarget`** — replaces four `stopPropagation` calls (close button, both arrows, stage wrapper) with one invariant in one place, over an `eslint-disable`. Checked first that no React ancestor of the portal has a click handler, since portal events bubble through the React tree rather than the DOM tree.

### Tradeoffs

- **Fade kept, movement removed** — reduced-motion visitors still get the 0.3s opacity fade and the hero's stagger delays; only positional keys snap. Standards-aligned (cross-fades are the recommended replacement for motion), confirmed with the user. Reversibility: easy.
- **`ThemeToggle`'s sliding pill now jumps** under reduced motion — Framer forces layout animations to `delay: 0, type: false`. Correct behaviour, but it is a deliberate design touch losing its slide. Reversibility: easy.
- **The provider is implicit** — nothing at a `fadeUp` call site shows reduced motion is handled. Bought one insertion point that cannot be forgotten; paid with indirection, mitigated by the `fadeUp` docblock and two tests. Reversibility: easy.

### Environment / Config Changes

- `eslint-plugin-jsx-a11y@^6.10.2` added as a devDependency (already hoisted as a transitive dep of `eslint-config-next`, so it resolves to the same instance). Recommended set now enabled in `eslint.config.mjs` with the three options above.

### What did I, Claude Code, or my agents learn from this

- **Framer Motion ignores `prefers-reduced-motion` by default** — `MotionConfigContext` ships `reducedMotion: "never"`, so every `motion` component in an app opts out until something opts in. Worth checking on any project using it.
- **Read the installed library source, not the docs, when the answer is load-bearing** — the whole design here rests on three facts found in `motion-dom`: positional keys (`x/y/scale/rotate/width/height`) get `{ type: false }` while opacity keeps its transition, layout animations get `delay: 0, type: false`, and `useReducedMotion()` initialises from `matchMedia` inside the hook body rather than in an effect. The last one is what rules out the obvious hook shape.
- **Mutation-test every new guard test before claiming it works** — broke the layout nesting and pointed the backdrop at bare `onClose`; both new test pairs failed as intended. Cheap, and the alternative is shipping an assertion that never could fail.
- **A11y lint false positives cluster on the most accessible code** — all four here fired on deliberate, commented workarounds. The right response is a rule option with the reason recorded, not an edit that makes the code worse to satisfy a linter.
