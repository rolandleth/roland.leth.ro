- `src/app/api/admin/posts/`, `…/posts/[id]/`, `…/posts/bulk/`, `…/projects/`, `…/projects/[id]/` — admin write API. One `[api:admin:posts:BULK] inserting` breadcrumb logs prepared slugs before the DB call so a subsequent 500 still tells us which were in-flight; `emitSkipSummary` emits `reasonsByType` on any non-empty `skipped`.
- `src/app/api/admin/revalidate/` — session-gated `POST` taking `{ posts?; projects?; guides? }`, each `"all" | string[]`: `"all"` busts every detail page of that type (`revalidateAllPosts`/`revalidateAllProjects`/`revalidateAllGuides`), an array busts only the named ones — posts as `section/slug`, projects as slugs, guides as slugs (each guide slug busts both `revalidateGuide` and `revalidateGuideTopic` since a slug can name either, and a topic publish-state flip should use `"all"`). Post entries must be exactly two segments with a known section — anything else lands in the response's `skipped`, never silently dropped; responds `{ ok, applied, skipped }` (skipped keys only when non-empty) and logs the same, so a bust that did nothing is distinguishable from one that ran [2026-07-17, after the stale-404 incident]. Companion to the direct-Prisma import scripts (which can't bust `unstable_cache` tags themselves); driven by the dashboard `RevalidatePanel`, into which the admin pastes the slug lists the import scripts print.
- `src/app/api/admin/keepalive/` — session-gated manual trigger; resolves the Redis client via the lazy memoized `getKeepaliveRedis()` from `@/lib/keepalive` and performs the same Upstash write as the cron route via the shared `writeKeepalive(redis)` helper. Parallel to `/api/cron/ping`, not bearer-shared: each route owns its own auth concern + status codes + log tags; only the client construction + write are centralized. 503 when Redis isn't configured (button can show a real error instead of pretending it worked); 502 on `redis.set()` reject; success line `[api:admin:keepalive] success` distinguishes manual triggers from scheduled cron in Vercel logs.
- `src/app/api/admin/indexnow/` — session-gated `POST` announcing every sitemap URL to IndexNow. Derives everything server-side (no request body): `getSiteUrl()` for the origin, `getIndexNowKey()` for the key, `await sitemap()` as the single URL source, so new posts/projects/guides need no upkeep. `?dryRun` previews the partitioned URL list without egress — an explicit falsy value (`false`/`0`/`no`/`off`) disables it via `isDryRunRequest`, because presence-only parsing made `?dryRun=false` return a 200 that looked like a completed submission. `describeKeyProblem` is the single source for both the dry-run warning and the real path's 503, so the two can't drift; the key's format is checked here rather than in the env schema. Status codes follow `keepalive`'s precedent — 503 for deploy-config gaps (missing/malformed key, non-public origin), 422 when the sitemap yields nothing this host can claim, 502 when IndexNow rejects a batch. Off-host URLs are partitioned out via `findForeignHostUrls` and reported in `skipped` rather than dropped.
- `src/app/indexnow-key.txt/` — public `GET` serving `INDEXNOW_KEY` verbatim as `text/plain`; 404s when unset. The key is a public verification token by design, not a secret — serving it openly is how the protocol works. `export const dynamic = "force-dynamic"` (the only one in the codebase) so the env value isn't baked at build time, plus `Cache-Control: no-store` so rotating the key takes effect on the next crawl. Folder name is the literal URL segment and must stay in lockstep with the `keyLocation` template in the submit route — renaming one breaks verification with a 403.
- `src/app/api/admin/upload/` — Vercel Blob upload (moved from `/api/upload` so the route is auth-gated by the generic `startsWith("/api/admin/")` gate in `src/proxy.ts` — one namespace, one gate, no per-path exception). Gated on `ALLOW_UPLOADS=true` (lazy-read so `vi.stubEnv` works); Content-Length precheck before `formData()` parse, then magic-byte sniff via `detectImageMime` (PNG/JPEG/GIF/WebP/AVIF) rejects payloads mislabelled as allowed image MIMEs. 413/415 paths log at warn. The malformed-multipart 400 routes the parser's `error.message` through `sanitizeLogString` (strips CR/LF/TAB/NUL, clamps to 200 chars) before logging — closes a log-injection vector where attacker-controlled boundary bytes in `error.message` could forge fake log lines beneath the real one. Log tag is `[api:admin:upload:POST]` to match the path-shape convention used elsewhere. The `detectImageMime`/`sanitizeLogString`/`sanitizeFilename` helpers live in a sibling `uploadHelpers.ts` — a `route.ts` may only export HTTP handlers + route-segment config, so test-imported helpers can't sit in the route file.
- `src/app/api/auth/login/`, `…/auth/logout/` — public auth entry. Login uses Upstash rate-limit, per-IP when `IP_HASH_SECRET` is set: `bucketKey(request)` (resolved once per request, shared by the limiter and the invalid-credentials log so the HMAC runs once and the two can't drift) returns `clientBucketKey(request, secret)` (HMAC-SHA256s the leftmost `x-forwarded-for` IP, truncates to 22 base64url chars, prefixes `ip:` so the per-client keyspace is formally disjoint from the `"global"` fallback under the shared `rl:login` Redis prefix) when the secret is present, else the constant `"global"` bucket. The limiter is built whenever `getRedisConfig()` is non-null; `getIpHashSecret()` controls only granularity, NOT whether the limiter runs — a missing secret while Redis is set logs a module-load warn and degrades to the shared global bucket (re-accepting a botnet admin-lockout DoS as the lesser evil over no limiter; never regresses to plain-IP keys). Plain SHA-256 was rejected because the ~4B IPv4 keyspace is brute-forceable; HMAC with a server-held secret blocks rainbow-table reversal. Leftmost-XFF trust is Vercel-specific (documented in-code; attacker-controlled behind an untrusted proxy). Log levels split by severity: 429 rate-limit-exceeded at `info` (routine hostile traffic), fail-open on an Upstash error at `error` (Redis down is operator-actionable), invalid-credentials at `warn` always carrying the resolved bucket key (`"global"` when no secret — never a raw IP) for correlation, success at `info`. Try/catch fail-open on Upstash errors so a Redis blip doesn't lock the admin out.
- `src/app/api/cron/ping/` — Vercel cron keepalive (daily at 00:00 UTC per `vercel.json`); constant-time Bearer check; resolves the Redis client via the lazy memoized `getKeepaliveRedis()` from `@/lib/keepalive` and performs the Upstash write via the shared `writeKeepalive(redis)` helper. `SET` not `PING`: Upstash excludes `PING` from idle detection, and the timestamp value doubles as an observable "last successful run" marker in the data browser. Emits `[api:cron:ping] success` info line on every successful write so "no cron success in N hours" alerting can be a log grep instead of an Upstash scrape (mirrors the admin route — together they answer "who wrote this timestamp"). Auth is now the shared `requireCronAuth(request, tag)` from `@/lib/api/cronAuth` (missing `CRON_SECRET` returns 401, not 500 naming the env var, while the server-side `console.error` preserves operator visibility; unauthorized hits log at warn).
- `src/app/api/cron/revalidate-scheduled/` — hourly Vercel cron (`0 * * * *` per `vercel.json`) that surfaces scheduled posts and guides whose publication time has passed. This is the ONLY mechanism that does so: every other path that changes the live content set is a mutation that revalidates its own tags, but a `datetime`/`publishedAt` crossing is not a mutation, so nothing else runs at that moment. Finds due content via `findPostsBecameLive` (a `yyyy-MM-dd-HHmm` string window) + `findGuidesBecameLive` (a real `DateTime` window), which return IDENTITIES rather than counts: the length decides whether to bust, and the slugs let each due item's own detail tag be busted via `revalidatePostDetails`/`revalidateGuideDetails` [2026-08-17]. That second half is load-bearing — detail entries (post page, its `.md`, guide page) carry only `post-{section}-{slug}`/`post-pages` and `guide-detail-{slug}`/`guide-pages`, which `revalidatePostSection`/`revalidateGuides` never touch, so a request landing while content was still future-dated pinned a 404 that survived until the next manual save. `WINDOW_HOURS = 49` is deliberately WIDER than the cron interval — overlap costs one redundant revalidation, a gap strands content silently; raise both together. Replaced the `revalidate = 3600` that the feed, archive and sitemap each carried, which regenerated all three every hour whether or not anything changed [2026-08-15]. The no-op run logs a `nothing due` heartbeat so a silently dead cron is greppable — without it, "nothing due" and "not running" look identical, and a dead cron now strands every scheduled post.
