## Session 1

### Decisions

- **`.md` variants prerendered per post** — `force-static` + `generateStaticParams` sharing `getAllPublishedPostSlugs` with the post page, so both views of a post always generate as a pair. Rejected leaving it dynamic: that kept a per-request invocation and a hand-set `Cache-Control` no tag bust could purge.
- **Kept the hand-built plain-text 404 in the `.md` route** — probing showed `notFound()` renders get cached too, so switching would not have avoided pinning and would have cost the machine-facing body. Reasoning inverted mid-session: first proposed on politeness grounds, then justified by the `.meta` recording `"status": 404` where the page's records nothing.
- **Cron returns identities, not counts** — `findPostsBecameLive` / `findGuidesBecameLive` replace the `count` queries so each due item's own detail tag can be busted. Rejected a blanket `POST_PAGES_TAG` bust: one due post would regenerate every post's page and `.md`.
- **Route groups over deleting every boundary** — `(list)` and `(gallery)` scope each list skeleton to its own page, adding no URL segment. Rejected deleting all four `loading.tsx` (lost five skeletons instead of three) and keeping them (left the soft 404s in place).
- **`dynamicParams = false` on `/blog/:section` and `/blog/:section/archive`** — their params come from the `SECTIONS` constant, so an unknown section is always a bad URL and Next serves `/_not-found` without rendering. Not applicable to DB-backed routes, which would 404 new content until the next deploy.
- **Rejected a `noindex` mitigation** — user called it correctly: it papers over a wrong status rather than fixing it, and the root cause turned out to be findable.

### Tradeoffs

- **Static `.md`** — gained zero function invocations on the rewrite and a tag-purgeable cache entry (fixing an up-to-1h stale window after an edit); accepted that a scheduled post's 404 now needs the cron bust to clear. Reversibility: easy.
- **Route groups** — kept the blog list and projects gallery skeletons, accepted losing three detail/pagination ones plus structural indirection that needs a comment to survive refactoring. Reversibility: easy.
- **Per-item detail busts over a blanket tag** — gained precision (two entries per due item); accepted a `findMany` where a `count` used to run. Reversibility: easy.

### Incidents / Bugs

- **Soft 404 across three routes, live in production** — `/blog/:section/:slug`, `/blog/:section/p/:page`, and `/projects/:slug` rendered the 404 page under a 200 status, advertising every guessed slug (and any scheduled post fetched before its `datetime`) as a real page. Root cause: a `loading.tsx` creates a Suspense boundary over its segment *and every route nested below it*; the boundary lets React commit a 200 and stream the shell before the page resolves, and a status cannot be revised after the first byte, so `notFound()` only swapped the boundary's content and never reached the `catch` in `app-render.js` that assigns `metadata.statusCode`. Fixed by scoping the two list boundaries into route groups and deleting the two detail ones. Regression risk is high and invisible — hence the filesystem guard.
- **Scheduled content stranded behind a pinned 404** — detail entries are prerendered with no time-based expiry (`initialRevalidateSeconds: false`, no fallback expiry), and carry `post-{section}-{slug}` + `post-pages`. `revalidatePostSection` busts none of those, so a request landing while a post was still future-dated pinned a 404 that survived until the post was next saved in admin. Guides had the identical shape via `guide-detail-{slug}` + `guide-pages`. Fixed by having the cron bust each due item's detail tag.

### What did I, Claude Code, or my agents learn from this

- **Structural reasoning was wrong every time; artefacts were right every time.** Four confident mechanism claims failed — that detail pages didn't pin 404s, that guides was affected, that `connection()` would preserve the status, that `generateMetadata` would escape the boundary. Every correct conclusion came from reading a `.meta` file or probing a build. When a claim is about framework behaviour, probe before asserting.
- **`.next/server/app/**/*.meta` is the cheapest diagnostic available.** It records `"status": 404` when the status was set and omits the field entirely when it wasn't, so comparing two routes' `.meta` files localises this class of bug in seconds without a deploy.
- **The route that *worked* was the clue.** Guides was the only detail route returning a real 404, and dismissing that as unexplained nearly cost the root cause. An outlier that behaves correctly is as diagnostic as one that fails.
- **Journal notes age out of truth.** A July entry recording "404 probes hit the DB on every request" was treated as current evidence and had stopped describing the build. Date-stamped observations about framework behaviour need re-verification, not citation.
- **`curl -I` sends HEAD, which is handled on a different path than GET.** An early probe reported a misleading status because of it; use `-o /dev/null -w "%{http_code}"` instead.
- **A build that predates a revert will happily test the reverted code.** Cost one confusing 500 attributed to a live bug rather than a stale binary; state the build/edit ordering when asking someone else to probe.

### Notes

- `metadata.statusCode` is assigned in a `catch` in `node_modules/next/dist/server/app-render/app-render.js` — the boundary is what prevents the `notFound()` error from ever reaching it. Next 16.3.1.
- Tag propagation from `unstable_cache` up onto a route-cache entry is confirmed by artefact, not inference: a prerendered `.md` entry's `x-next-cache-tags` carries `post-tech-{slug}` and `post-pages` alongside Next's own `_N_T_` tags.
- `/blog/:section/search` was never affected — it has no `generateStaticParams`, so it renders per request and writes no cache entry.
- Pagination pages were already covered for scheduled content, because `BlogPostList` reads the `blog-{section}`-tagged cache *before* calling `notFound()`, so even a pinned out-of-range 404 carried a tag the cron busts. Detail pages read only per-post tags, which is why they alone were stranded.
