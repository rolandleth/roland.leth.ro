## Session 1

### Incidents / Bugs

- **Swipe still opened the lightbox (recurring)** — the 2026-07-07 fix set `suppressEnlargeRef` inside `handleDragEnd`, on the assumption it fired before the browser's trailing `click`. It doesn't: framer-motion v12 fires `onDragEnd` via `frame.postRender(...)` (`node_modules/framer-motion/.../VisualElementDragControls.mjs:174`), i.e. the *next frame* — after `pointerup` → `click`. So the click read the flag as still-`false` and enlarged. Fix: arbitrate swipe-vs-tap from the raw pointer instead — `onPointerDownCapture` records `clientX` (+ resets the flag), `onPointerUpCapture` sets the flag when travel > `SWIPE_CLICK_TRAVEL` (8px); both guarded on `event.isPrimary`. `pointerup` dispatches before `click`, so the guard is set in time. Removed the too-late set from `handleDragEnd`. In `ProjectSectionCarousel.tsx`; 2 tests added.
- **Accelerated / "weird" animation swiping across sections** — the section tabpanel `<div key={activeSection.id}>` wraps the continuous carousel. A cross-section swipe changes `activeTab` → the key changes → React remounts the whole carousel: its `x` `MotionValue` resets to 0 and `useElementSize` re-measures from 0, so it snaps to slide 0 and springs across *every* slide to the new flat index (a fly-across) instead of stepping one slide. Within-section swipes don't touch `activeTab`, which is why only crossings misbehaved. Fix: dropped the `key` so the panel (and carousel) keep stable identity; `id`/`aria-labelledby` swap as attributes on the same node. In `ProjectContent.tsx`; 1 identity-based regression test added and confirmed to fail when the key is re-added.

### What did I, Claude Code, or my agents learn from this

- **Framer's `onDragEnd` can't gate the browser's post-drag `click`** — it's deferred via `frame.postRender`, so it lands a frame after `pointerup`/`click`. For click-vs-drag suppression, read the raw pointer at `pointerdown`/`pointerup` (which strictly precede `click`), never `onDragEnd`. The prior "deterministic, doesn't depend on framer" claim was exactly backwards.
- **A `key` on a container remounts its entire subtree** — dangerous when a stateful/continuous child (here a carousel holding framer `MotionValue`s) sits inside a per-section-keyed panel. If a child must persist across the parent's identity changes, it can't live under that key.

### Notes

- Correction to 2026-07-07's journal: the `suppressEnlargeRef` approach was described as framer-independent and deterministic. It depended on `onDragEnd` beating the click, which never happens. Don't trust that earlier note on recall.

## Session 2

### Decisions

- **Lightbox stage cursor is now default when not zoomed** — dropped `cursor-zoom-in` from the stage in `ProjectImageLightbox.tsx`; `cursor-grab` stays for the zoomed/pannable state. The carousel's `cursor-zoom-in` in `GalleryTrack.tsx` was deliberately kept — it only renders with `onActivateSlide` (the click-to-enlarge affordance), which the lightbox never passes.
- **Gallery stage hugs content via `aspect-[1270/760]` + `max-h` caps** — replaced the fixed `h-[60vh] sm:h-120` stage in `ProjectSectionCarousel.tsx` with an aspect-ratio-driven height capped at the old values (`max-h-[60vh] sm:max-h-120`), killing the huge vertical letterbox on mobile. Rejected: storing intrinsic width/height per `ProjectSectionImage` (schema migration + import-script measuring + admin upload plumbing — user called it out of proportion for the goal) and client-side natural-size measurement (layout shift as lazy slides load).

### Tradeoffs

- **Ratio is pipeline-coupled, not content-derived** — gained a one-class fix with zero data-model changes; accepted that the 1270×760 assumption lives in a Tailwind class (see new watch-out). Reversibility: easy — the rejected DB-dims design is written up in this entry if exact per-gallery heights are ever wanted.

### What did I, Claude Code, or my agents learn from this

- **`Read` renders local images, which is enough for layout forensics** — verified both projects' staged marketing shots are 1270×760 by reading the PNGs directly (rendered size in the tool result), avoiding any image-measuring dependency or script just to pick the stage ratio.
- **`aspect-ratio` + `max-height` compose cleanly for "hug but stay bounded"** — the box takes `width/ratio` until the cap wins, and `object-contain` absorbs any mismatch, so a fixed-height stage can become content-hugging without touching the slide strip's stable-height contract.

### Notes

- The two staged galleries (`scripts/imports/reckon`, `scripts/imports/continuum`) both ship 1270×760 shots — the app-copy image pipeline's shape; that's what makes the hardcoded ratio safe today.
