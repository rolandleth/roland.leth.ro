## Session 3

### Decisions

- **Suppress entrance animations on browser back/forward** — root cause: `fadeUp`'s `initial → animate` runs on every mount, and Next App Router remounts the route subtree on `popstate` (no bfcache for soft navigations), so every back/forward replays the page's entrance. Fix: a module flag mirrors the last navigation type; `fadeUp` returns `initial: false` when it was a back/forward, jumping straight to the resolved state. Centralised in `lib/client/motion.ts` + `lib/client/navigationType.ts` + a `NavigationTypeTracker` island in the root layout — zero per-page/per-call-site edits.
- **Navigation API over History monkey-patch** — for the detection mechanism, chose the Navigation API's `currententrychange` event (reports `navigationType`) over patching `history.pushState`/`replaceState`. The plain History API fires *no* event for push/replace (only `popstate` for back/forward), so the patch would be the only way to get the forward-nav reset signal — but the user objected to reassigning the global history closures. (Rejected the hybrid: it's strictly more code and still contains the patch behind a feature-detect.)
- **`currententrychange`, not `navigate`** — the better-known `navigate` event does *not* fire for `history.pushState`, which is exactly how Next does client navigation, so it'd never reset the flag on a forward nav. `currententrychange` fires for pushState and carries `navigationType`.
- **Inline cast over an ambient `.d.ts`** — `window.navigation` isn't in TS 5.9.3's `lib.dom`, and `lib` can't supply it (no Navigation-API lib entry; the types live inside the generated `lib.dom.d.ts`, which lacks them). Considered a `@types/dom-navigation` dep and a hand-written ambient `src/types/navigation-api.d.ts` (briefly created, then deleted); settled on a contained inline cast in `navigationType.ts` since there's a single consumer — no dependency, no project-wide `Window` augmentation.

### Tradeoffs

- **Navigation API + graceful degradation** — gained clean runtime (no monkey-patching) and contained typing; accepted that Firefox / older Safari keep replaying the entrance on back. The degradation equals prior behaviour, so nothing breaks. Reversibility: easy (History-patch covers all browsers if parity is ever needed).

### Incidents / Bugs

- **SSR `ReferenceError` in the inline-cast version** — first inline draft read `window` *before* the `typeof window === "undefined"` guard, which would throw during server rendering. Caught immediately; reordered so the guard runs first, then the `window.navigation` feature-detect.

### What did I, Claude Code, or my agents learn from this

- **The History API has no push/replace event** — `history.pushState`/`replaceState` fire nothing; `popstate` is back/forward only. That's why pushState-patching is a ~15-year idiom. The modern, patch-free alternative is the Navigation API, and the right event for catching SPA pushState navigations is `currententrychange` (not `navigate`).
- **`lib` only includes TS's shipped lib files** — you can't add a DOM API via `lib`; browser API types live in the generated `lib.dom.d.ts`, and the Navigation API isn't in it as of TS 5.9.3. The enum-like `NavigationType` *is* a known global, but the `Window.navigation` property is not.

### Notes

- New files: `src/lib/client/navigationType.ts` (+ test), `src/components/NavigationTypeTracker.tsx`. Modified: `src/lib/client/motion.ts` (`fadeUp` now returns `initial: false | {...}`), `motion.test.ts` (mocks `navigationType` to cover the back/forward branch), `src/app/layout.tsx` (mounts the tracker). tsc, lint, and the touched tests pass.
- Scope: only `fadeUp`-based entrances are suppressed (projects list, `ProjectContent`, FAQ, `FadeIn`, `HomeHero`, blog post content). Raw-`motion` components (`Typewriter`, the intra-page `AnimatePresence` tab-switch in `ProjectContent`) are unaffected by design.

## Session 5

### Decisions

- **Escape JSON-LD at the embedding boundary, not at the data layer** — `safeJsonLdString` in `src/lib/content/projectJsonLd.ts` escapes `<`/`>`/`&`/U+2028/U+2029; applied at the two `<script>` sites in `src/app/projects/[slug]/page.tsx`. Alternatives: validate at the zod schema (rejected — risk is at HTML embed, not data write); switch to `<script>{json}</script>` children form (rejected — same escape requirement, cosmetic only). `dangerouslySetInnerHTML` is the React-recommended pattern for inline JSON-LD; the `dangerously` prefix flags responsibility, which the escape discharges.
- **Multi-currency offers emit an array of `Offer` nodes, not a mislabeled `AggregateOffer`** — `AggregateOffer.priceCurrency` asserts one currency across the price range, so silently picking `offers[0].priceCurrency` for a USD+EUR mix would lie about one bound. Schema.org permits `offers: [Offer, Offer, ...]` for the mixed case. (Alternatives: throw / drop — rejected as array is the schema-correct fallback.)
- **FAQ Markdown failure renders a fallback `<p>`, not a 500** — `Promise.allSettled` in `src/app/projects/[slug]/page.tsx`, per-FAQ `<p>{f.answer}</p>` on rejection plus `console.error` for server logs. Alternative: validate Markdown at admin submit (rejected — larger surface; fallback is the smallest behaviour change with highest user value).
- **`<html data-navigation-api="available|missing">` for fallback observability** — tagged once in `installNavigationTypeTracking()`. Alternative: `console.warn` (rejected — invisible without DevTools); telemetry counter (rejected — one-bit signal doesn't earn the plumbing). The DOM attribute is the cheapest diagnosable hint without changing the silent-degradation contract.
- **Author entities carry `url: base`** — applied to `buildSoftwareApplicationJsonLd` and (via a new `personFor(base)` helper, refactored from the module-level `PERSON` const) `buildBlogPostingJsonLd`. Triggered by Google's Rich Results validator flagging `author.url` as a missing optional field; the site origin is the author's homepage, so no invented data.
- **Import script's `$transaction` runs at Serializable isolation** — matches the API routes (`POST` / `PUT /api/admin/projects[/:id]`), so a concurrent admin edit can't slip a non-repeatable read between the delete-and-create on the same slug. Alternative: keep READ_COMMITTED (rejected — eliminates the only known race window with near-zero cost).
- **Skipped `aggregateRating`, `useCallback` on lightbox handlers, ogTitle length cap, body-scroll lock stack** — `aggregateRating` requires real user numbers (inventing them violates Google's quality guidelines); the rest are flag-only items where the fix cost outweighs the benefit at current scale.

### Tradeoffs

- **`safeJsonLdString` regex built from a string** — `new RegExp("[\\u2028\\u2029]", "g")` rather than a regex literal `/[  ]/g`, because literal line-separator chars in source terminate the regex literal. Reversibility: easy; one extra module-level constant.
- **`Promise.allSettled` for FAQ rendering** — gained resilience against bad Markdown, accepted that a broken answer falls back to plain text without Markdown formatting (the `FAQPage` JSON-LD still ships the raw answer string, so SEO isn't lost). Reversibility: easy.
- **Lightbox keyboard handler still rebinds per render** — review flagged that effect deps include `onClose`/`onPrev`/`onNext` and the parent passes inline arrows, so the listener detaches/reattaches every render. Accepted the churn rather than the ref dance to stabilize closures over moving state. Reversibility: easy.

### Incidents / Bugs

- **Carousel `onLoad` race wasn't reproducible** — review speculated an in-flight `onLoad` could fire after src change. Verified that browsers abort in-flight image loads when src changes, so the aborted request never fires `load`. Dropped the speculative race fix; only the dev-warn for invalid dimensions was kept.
- **Gallery select "eagerly pulls FAQs" finding was wrong** — verified `gallerySelect` at `src/lib/db/projects.ts:101-129` does not include `faqs`. Caught mid-implementation; review file amended in wrap-up.
- **IDE LSP diagnostics drifted from `tsc`** — IDE flagged "unterminated regex literal" on `safeJsonLdString`, `tsc --noEmit` exited clean. Trusted tsc; root cause unconfirmed (likely stale parser state in the harness LSP).
- **Write tool normalized ` `/` ` escape sequences in TS source** — landed as the actual line-separator chars on disk, which then terminated JS regex literals. Worked around by building the pattern via `new RegExp("[\\u2028\\u2029]", "g")` where the escapes live inside a string literal, not a regex literal.

### What did I, Claude Code, or my agents learn from this

- **JSON-LD via `dangerouslySetInnerHTML` is canonical, not a flaw** — the React API name flags responsibility for escaping; the risk lives in the string, not the embed mechanism. The `<script>{json}</script>` children form works the same way and has the same escape requirement (HTML treats `<script>` as a raw-text container, so React emits children unescaped — escaping is still ours).
- **`jsonld` (the npm package) is the wrong tool for emitting structured data** — it's a processor for expansion/compaction/canonicalization (URDNA2015 for verifiable credentials, RDF dataset conversion). Adds ~250 kB for zero benefit. `schema-dts` (Google's TypeScript types for schema.org) is the actual lever if compile-time correctness matters.
- **`next/script` is for executable JS, not JSON-LD** — Next.js docs explicitly call this out; native `<script type="application/ld+json">` is the right choice.
- **Google Rich Results validator warnings are mostly optional-field hints** — `aggregateRating` (real numbers only; inventing them risks manual action), `screenshot`, `author.url` (cheap, honest one-liner). Honest default for personal portfolios is to omit fields you can't substantiate.
- **When IDE LSP diagnostics disagree with `tsc --noEmit`, trust tsc** — don't react to harness diagnostics without verifying.
- **Write/Edit tools may normalize Unicode escape sequences in TS source** — ` `/` ` written through Write may land as the actual line-separator chars on disk. Build the pattern via `new RegExp("[\\u2028\\u2029]", "g")` (escapes inside a string literal, not a regex literal) as the workaround.

### Decisions

- **Single chokepoint for JSON-LD injection** — extracted `<JsonLdScript data={…} />` (`src/components/JsonLdScript.tsx`) as the only component allowed to use `dangerouslySetInnerHTML`. It returns `null` for null/undefined data, so callers drop their `&&` guards. Chose this over leaving three hand-written `<script>` blocks across the blog + project pages (DRY; one place to audit; lets the lint rule guard the attribute, not the serializer call).
- **Lint guards the attribute, not the call** — replaced the lexical `JSON.stringify`-inside-`dangerouslySetInnerHTML` selector with a blanket ban on the `dangerouslySetInnerHTML` attribute, overridden off only for `JsonLdScript.tsx`. Closes the aliased-serialization gap noted in session 6's watch-out (a hoisted `const s = JSON.stringify(x)` or a different serializer now can't slip past).
- **`safeJsonLdString(undefined)` throws** — added an explicit `TypeError` guard; `JSON.stringify(undefined)` returns the value `undefined`, which previously made the `.replace` chain crash cryptically. Chose a loud throw over silently emitting `"null"` (no silent suppression; absent blocks are skipped upstream by `JsonLdScript`).
