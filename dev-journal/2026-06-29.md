- **Swipe via Framer drag** — horizontal `drag` layer over the slides (carousel) and on the stage `motion.div` (lightbox), gated on `canNavigate`, routed through the parent's existing `navigateImage` so swipes cross section boundaries like the arrows. ### Tradeoffs

- **Stage hugs the image** — gained tight, letterbox-free sizing; accepted a one-time height snap when the first image loads and per-image snaps across differing ratios. Reversibility: easy (revert to fixed `h-120`).
- **Swipe untested in jsdom** — shipped without a unit test rather than writing brittle pointer-event theater that Framer's gesture layer ignores. Reversibility: easy; covered manually instead.

### Incidents / Bugs

- **Black gradient only on real iOS Safari** — root cause: `to-transparent` interpolates toward transparent black; desktop responsive mode/simulator premultiply alpha differently and hid it. Fixed by fading to `--color-background-transparent`. Low regression risk.

### What did I, Claude Code, or my agents learn from this

- **`transparent` is transparent black** — fading any opaque colour to the `transparent` keyword produces a grey/black midpoint that Safari renders most visibly. Always fade to the same colour at zero alpha.
- **Framer drag + AnimatePresence** — keep the `drag` element separate from the keyed, x-animating slide (use a stable drag layer wrapping the `AnimatePresence`) so the gesture state and the enter/exit animation don't fight. `draggable={false}` + `pointer-events-none`/`select-none` on the image stops native image-drag from stealing the gesture; a sub-threshold tap still reaches the enlarge button.

## Session 3

### Decisions

- **Suppress entrance animations on browser back/forward** — root cause: `fadeUp`'s `initial → animate` runs on every mount, and Next App Router remounts the route subtree on `popstate` (no bfcache for soft navigations), so every back/forward replays the page's entrance. Fix: a module flag mirrors the last navigation type; `fadeUp` returns `initial: false` when it was a back/forward, jumping straight to the resolved state. Centralised in `lib/client/motion.ts` + `lib/client/navigationType.ts` + a `NavigationTypeTracker` island in the root layout — zero per-page/per-call-site edits.
- **Navigation API over History monkey-patch** — for the detection mechanism, chose the Navigation API's `currententrychange` event (reports `navigationType`) over patching `history.pushState`/`replaceState`. The plain History API fires *no* event for push/replace (only `popstate` for back/forward), so the patch would be the only way to get the forward-nav reset signal — but the user objected to reassigning the global history closures. (Rejected the hybrid: it's strictly more code and still contains the patch behind a feature-detect.)
- **`currententrychange`, not `navigate`** — the better-known `navigate` event does *not* fire for `history.pushState`, which is exactly how Next does client navigation, so it'd never reset the flag on a forward nav. `currententrychange` fires for pushState and carries `navigationType`.
- **Inline cast over an ambient `.d.ts`** — `window.navigation` isn't in TS 5.9.3's `lib.dom`, and `lib` can't supply it (no Navigation-API lib entry; the types live inside the generated `lib.dom.d.ts`, which lacks them). Considered a `@types/dom-navigation` dep and a hand-written ambient `src/types/navigation-api.d.ts` (briefly created, then deleted); settled on a contained inline cast in `navigationType.ts` since there's a single consumer — no dependency, no project-wide `Window` augmentation.

### Tradeoffs

- **Navigation API + graceful degradation** — gained clean runtime (no monkey-patching) and contained typing; accepted that Firefox / older Safari keep replaying the entrance on back. The degradation equals prior behaviour, so nothing breaks. Reversibility: easy (History-patch covers all browsers if parity is ever needed).

### Incidents / Bugs

- **SSR `ReferenceError` in the inline-cast version** — first inline draft read `window` *before* the `typeof window === "undefined"` guard, which would throw during server rendering. Caught immediately; reordered so the guard runs first, then the `window.navigation` feature-detect.

### What did I, Claude Code, or my agents learn from this

- **The History API has no push/replace event** — `history.pushState`/`replaceState` fire nothing; `popstate` is back/forward only. That's why pushState-patching is a ~15-year idiom. The modern, patch-free alternative is the Navigation API, and the right event for catching SPA pushState navigations is `currententrychange` (not `navigate`).
- **`lib` only includes TS's shipped lib files** — you can't add a DOM API via `lib`; browser API types live in the generated `lib.dom.d.ts`, and the Navigation API isn't in it as of TS 5.9.3. The enum-like `NavigationType` *is* a known global, but the `Window.navigation` property is not.
