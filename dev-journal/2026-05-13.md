### Decisions

- **`useOptimisticMutation` cleanup nulls `abortRef.current` in addition to aborting** — the unmount-after-resolve test I added on Phase 4 exposed that the existing `controller !== abortRef.current` supersession guard was satisfied by post-unmount continuations (ref still held the aborted controller), so `setState` could fire on an unmounted component. Nulling the ref in cleanup makes the guard correct for every post-unmount path, not just the abort-rejection one. Alternative considered: only abort — rejected, the test premise was sound and the gap was real.
- **`MutateResult` discriminant landed at 2 callers, not 3** — rule-of-three would have been more defensible, but the extraction tax for adding the discriminant later (touch every caller's destructure + audit `{ ok: false }` returns) outweighs the speculative-abstraction cost since both callers still just read `result.ok`. Returns primitives so neither caller is forced to handle the discriminant. Alternative considered: defer to the third caller — rejected, the seam is cheap to widen now and free to ignore at call sites.
- **`AdminAuditTag` derived from `const ADMIN_AUDIT_TAGS = [...] as const` array** — single edit site when adding a new admin write surface; the runtime list is greppable too. Alternative considered: hand-written union type — rejected, required editing both the union and re-scanning routes for typos every time.
- **Drop the `void` operator from fire-and-forget `mutate()` calls inside `act()`** — `sonarjs/void-use` and `@typescript-eslint/no-floating-promises` directly contradict on this pattern. Verified the project doesn't have `no-floating-promises` enabled (lint passed after removal). Block-body `act(() => { result.current.mutate(...) })` implicitly returns `undefined`, no further marker needed. Alternative considered: `.catch(() => {})` — rejected as more verbose with no readability gain; per-line `eslint-disable-next-line` — rejected as noisy.
- **`ProjectForm.handleSubmit` re-snaps from `sortOrderText` before submitting** — submit can fire before blur (Enter inside another input, Save click while sortOrder still has focus + transient invalid text). Pre-fix: typing `"5"` → deleting to `""` → submitting shipped the stale committed `5`. The re-snap applies the same digit-only-or-fall-back rule the blur handler uses. Alternative considered: commit invalid input immediately (clearing → `0`) — rejected, breaks the "echo what you typed until commit" UX the existing blur handler establishes.
- **`apiErrors.describeZodIssues` de-duplicates segments before applying `MAX_ISSUE_SEGMENTS` cap** — pathological payloads (30× the same `invalid_type` code, empty paths) used to render `"invalid_type, invalid_type, …, +20 more"` — log spam with no signal. `Array.from(new Set(rawSegments))` collapses dupes; the cap now bounds distinct segments. Alternative considered: keep dupes for "frequency signal" — rejected, the warn-level demotion means we don't want one malformed probe producing a multi-KB line either way.
- **Drop `formatZodIssues` export from `readErrorMessage.ts`** — only the same-file caller used it; the test only imports `readErrorMessage`. Hardened `path` filter in the same pass: drops `null`/`undefined`/`""` segments rather than rendering them literally (`"sections.0.undefined: Required"` is confusing UX). Alternative considered: keep the export for "future use" — rejected, YAGNI.
- **`sanitizeLogString` strips CR/LF/TAB/NUL + clamps to 200 chars before logging multipart-parser errors** — log injection via newline forgery is the primary vector; clamp protects against multi-KB error messages. Alternative considered: log only the error class name (no message) — rejected, the message has triage value when a real client bug surfaces.
- **`PrivacyPageLayout.tsx` `<main>` → `<div>`** — file wasn't in yesterday's 11-commit Phase 2 hoist; the code review caught it. `/privacy` and `/privacy/body-tracking` had been producing two `<main>` landmarks per document since the hoist. Alternative considered: defer to a focused a11y sweep — rejected, the journal's "code-review on any new top-level page" trigger explicitly called for fixing this now.

### Tradeoffs

- **Discriminant at 2 callers** — gained: future-proof failure-vs-supersession contract. Cost: code-shape change for a behavior neither caller exercises today. Reversibility: easy (collapse to `{ ok: boolean }` + delete the `reason` field at 4 return sites if no third caller materializes).
- **`abortRef.current = null` in cleanup** — gained: closes the unmount-after-resolve `setState` warning; the supersession guard now covers post-unmount continuations regardless of whether fetch observed the abort. Cost: very narrow — `abortRef` is now nullable after unmount, but no path reads it after cleanup. Reversibility: easy.
- **`sortOrderText` re-snap on submit** — gained: pre-blur submit can't ship a stale value. Cost: submit logic now has two sources for `sortOrder` (committed state + display text), one of which wins via the digit-only check. Slight cognitive load; mitigated by mirroring the blur handler's rule verbatim. Reversibility: easy.
- **Log payload clamp at 200 chars** — gained: bounded log lines; log injection defended. Cost: tail context lost when a real parser error has a long message. Reversibility: easy (raise `MAX_LOG_MESSAGE_LEN`).
- **`MutateResult` widened (`{ ok: true } | { ok: false; reason: ... }`)** — gained: discriminant for future consumers. Cost: callers destructuring `const { ok, reason } = await mutate(...)` would now get a TS error on the success branch (`reason` doesn't exist). Today's callers only read `ok` so they're unaffected; flag if a future caller wants both. Reversibility: easy.

### What did I, Claude Code, or my agents learn from this

- **A test you wrote can expose a real implementation gap, not just a coverage gap.** The unmount-after-resolve test in Phase 4 was meant to pin behavior I assumed was already correct (the existing supersession guard should suppress post-unmount continuations). It failed against the real hook. The gap was that cleanup aborted but didn't null `abortRef.current`, so a buffered fetch resolve could race past the abort signal and pass the guard. Generalizable: when a test premise that "should pass with the current implementation" fails, the first hypothesis should be "implementation has a gap," not "test is wrong."
- **Concrete trigger conditions in watch-outs do their job.** The 2026-05-12 watch-out about new pages adding their own `<main>` had an explicit trigger: "code-review on any new top-level page." The 2026-05-13 review fired on a *pre-existing* page (`PrivacyPageLayout.tsx`) that the hoist sweep missed. The watch-out caught what a vague "be careful about a11y" note wouldn't have. Will keep writing watch-outs with explicit triggers, not just "revisit later."
- **ESLint rule conflicts need an explicit decision, not a workaround.** `sonarjs/void-use` and `@typescript-eslint/no-floating-promises` directly contradict on `void promise`. The cleanest resolution is to confirm which rule is actually enabled and align with it — not to add `void` AND a disable comment. Verified empirically (yarn lint passed after `void` removal) rather than assuming.
- **Discriminant unions land cheap when callers destructure just the shared discriminator.** `{ ok: true } | { ok: false; reason: "failure" | "superseded" }` widened the hook's return type, but both existing callers continue to destructure `const { ok } = await mutate(...)` — `ok` is `boolean` on the union, so no caller change needed. The "rule of three" doesn't apply when the abstraction extension is invisible to existing consumers. Will use this pattern when a primitive `boolean` could benefit from future-proofing without forcing call-site churn.
