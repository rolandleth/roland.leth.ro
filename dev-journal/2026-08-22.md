## Watch-outs & Tech Debt

- **`stripComments` in `src/test/sourceText.ts` is a naive scanner, not a tokenizer** — it does not know about string, template, or regex literals, so a `"//"` inside a string truncates that line and a `"/*"` swallows source to the next close. Every failure mode is a false POSITIVE (a match disappears, the test fails loudly), which is the safe direction for a guard, so it is deliberately not a tokenizer. Revisit when a source-text test starts failing for a reason nobody can explain, or when a guarded file gains a literal containing comment syntax; the upgrade path is TypeScript's own `createScanner`, already available via the installed `typescript` package.
- **`errorDetails`' return contract is deliberately wide** — every own enumerable property of an `Error` reaches the log line, unredacted and unbounded. Correct for Prisma's `code`/`meta`/`clientVersion`, and harmless today because this codebase defines no `Error` subclass of its own. It stops being harmless the moment one carries a request body, a token, or a large payload. Revisit when the first custom error type is written, not before — a denylist that has never been exercised rots.
- **Three tests now assert on source text** (`searchParams` absence in `blog/[section]/(list)`, the `cache()` wrapper in `blog/[section]/p/[page]`, the `await` on `requireAdminPageSession` in `adminPageContract`). Each exists because the thing it protects is syntactic and has no runtime surface a unit test can observe. They are also the easiest kind of test to write vacuously. Every one of them should be verified by breaking the thing it guards and watching it fail; the `await` one was, this session. Revisit the other two the next time either file is touched.
- **`makeBlogPageCache` reads `getSectionPageCount` from inside its own `unstable_cache` callback** — one cache entry reading another. The callback only runs on a miss, so a warm page entry returns a `totalPages` frozen at its own last generation while `isRealPage` reads the count entry's current value. Same tag on both, so a bust converges them; between the bust and regeneration they can differ. `BlogPostList`'s `page > 1 && posts.length === 0` check is the backstop. Now documented in the docblock. Revisit if a third reader of the page count appears, since it would need the same backstop reasoning.

## Session 1

### Decisions

- **Made `errorDetails` genuinely JSON-safe rather than documenting the hole** — the alternative was leaving the spread as-is and qualifying the docblock's "JSON-safe object" claim. Chose the filter because the failure it prevents is a throw raised *while reporting an error*, which loses the original error entirely: strictly worse than the dropped `stack` the function was written to prevent.
- **`isJsonSerializable` defers to `JSON.stringify` in a `try`/`catch` rather than type-checking values** — a hand-written "is this a primitive" walk rejects a `Date` (and anything else with `toJSON`) that the real serializer accepts, and the set of things `JSON.stringify` rejects is its own to define. Reimplementing that judgement is how the two drift apart.
- **Moved `feedTag` from `content/feed.ts` to `db/posts.ts`** (vs. a new neutral `cacheTags` module, vs. leaving it) — every other cache tag in the codebase is minted and busted from the db layer, and `sectionTag` already lives there. The feed route already imported `bySection` from `posts.ts`, so it took no new dependency. A third module would have been a new boundary to justify for one function.
- **Extracted `stripComments` into `src/test/sourceText.ts`** rather than fixing the one test that prompted it — the same need existed in three places, and the paginated route's copy was the worse instance: its `cache()` assertions are *presence* checks, so a comment mentioning `resolvePage = cache(` would have satisfied them against a page that no longer wrapped anything.
- **Collapsed the four repeated edit-page comments to a two-line pointer** — the four-line explanation existed verbatim at each call site plus in `requireAdminPageSession`'s docblock. Kept the "required even though `generateMetadata` is guarded" signal at the call site (that is the non-obvious part a reader needs *there*) and left the reasoning in one place.
- **Recorded `AdminPagination`'s Suspense dependency in `loadingBoundaries.test.ts`, not only in the component** — that file is where someone adding a `loading.tsx` would look, and its header previously framed the constraint as being about 404 status alone. `/admin` is not in `ROUTES_REQUIRING_REAL_404` (it has no 404 path) but its out-of-range `redirect()` and every protected page's auth redirect have the identical dependency.

### Tradeoffs

- **`errorDetails` now runs `JSON.stringify` once per own enumerable property** — gained a guarantee that holds for any error shape, accepted a serialization pass over fields that are almost always three or four small values on an error path that is already the slow path. Reversibility: easy, pure function.
- **Documented `errorDetails`' wide contract instead of adding redaction** — gained no unexercised machinery, accepted that the guard against logging a sensitive field is a docblock and a reader, not code. Defensible only while no custom error type exists; see Watch-outs.
- **The `await` contract test asserts on source text** — gained coverage of a failure mode with no runtime signal (an unawaited guard still "runs", just after the data read), accepted a test that a sufficiently creative refactor could evade. Verified by breaking it, which is the only thing that makes this kind of test worth having.

### Incidents / Bugs

- **`errorDetails`' JSON-safety hole was introduced by the previous session's own remediation** — the 2026-08-21 widening from `{message, stack}` to a full spread was a correct fix for a real problem (Prisma's `code`/`meta` being traded away) that silently voided the function's stated guarantee. No live defect: nothing in this codebase throws an error carrying a `BigInt`, a cycle, or a function. Found by reviewing the fix rather than the original bug.
- **The `admin page-body session guard` contract test could not fail for the case it was written for** — it matched `source.includes("requireAdminPageSession(")`, which an unawaited call satisfies. `requireAdminPageSession` reaches its `redirect()` only after `await verifySession()`, so a floating call returns a pending promise and the page's next line — the data read — runs first. The function's own docblock names this hazard and notes that `eslint.config.mjs` uses `tseslint.configs.strict` (not `strictTypeChecked`), so `no-floating-promises` is off and nothing else catches it. Fixed and verified by removing an `await` from `guides/new/page.tsx` and confirming that test, and only that test, failed.

### What did I, Claude Code, or my agents learn from this

- **A guard that has never been seen to fail is a guard nobody has tested.** Both of this session's highest-value findings were tests that read as thorough and could not fail: the contract test's missing-`await` blind spot, and the gallery test asserting two names render when it claimed to assert grouping. The cheap check is to break the thing and watch the test go red — done for the `await` test here, and worth doing for any source-text assertion.
- **The 2026-08-21 watch-out about back-to-back review passes generalised.** That entry noted a review-then-fix pass can itself introduce gaps large enough to need another pass. This session is the third instance: the `errorDetails` widening (a fix) created the JSON-safety hole, and the contract test (a fix) shipped with a hole in the assertion. Reviewing remediation commits specifically — not just original code — keeps paying.
- **When a fix's docblock explains a consequence, check whether it names the mechanism.** `makeBlogPageCache` accurately described *that* `totalPages` could go stale and *that* a backstop existed, but never said the cause was one `unstable_cache` reading another. A reader following "shared cache entry" to "and yet a backstop is needed" had no way to connect the two.
