## Session 1

### Decisions

- **Repair the `undefined` feed URLs with a redirect, not a 404** — added a 308 in
  `LEGACY_REDIRECTS` for `/api/feed/undefined/blog/:section/:slug`. Rejected leaving them to
  the static 404 (it still renders a full page, see Incidents) and rejected a `410 Gone` route
  handler (puts billed compute back on scanner traffic, the exact thing the root-level legacy
  slug route was deleted to avoid).
- **Slug pinned to `[a-z0-9-]+` on the new rule** — mirrors `createSlug`'s alphabet, so a
  malformed tail 404s directly rather than redirecting into a 404. Same reasoning as the
  `[1-9]\d*` page pattern.
- **Did not re-add `LEGACY_POST_SLUG_ALIASES` as static rules** — the cost premise was right
  (Vercel's routing layer, no invocation, no perceptible UX), but the removal reason was zero
  traffic, and that is unchanged. Checked the seven dirty slugs against the 404 report: no
  hits. Cheap is not the same as worth it.

### Incidents / Bugs

- **`/api/feed/undefined/blog/tech/<slug>` 404s in Speed Insights** — root cause: the first
  Next feed route (`5ae079ec`, 2026-04-05) built entry URLs from `process.env.NEXTAUTH_URL`,
  a variable this project never set (auth is custom `jose` + `bcryptjs`). Every `<link>` and
  `<id>` went out as the relative reference `undefined/blog/:section/:slug`, which consumers
  resolved against the feed's own URL — base directory `/api/feed/` — producing the observed
  paths. Fixed in `3d4f8759` / `867907ff` on 2026-04-07, so the exposure was two days; the
  crawl memory outlived it by five months. Only 2018–2020 slugs appear because those were the
  newest twenty posts in April 2026. No regression risk: `getSiteUrl()` either returns a
  validated origin, falls back to the Vercel host, or throws.

### What did I, Claude Code, or my agents learn from this

- **"Zero server compute" is not "no cost"** — the prerendered 404 is genuinely static
  (`_not-found.meta` carries `"status": 404` and `x-nextjs-prerender: 1`, and `/_not-found` is
  in the prerender manifest), but it is still a full page: the root layout wraps it, and the
  root layout mounts `<SpeedInsights />` through `ClientAnalytics`. Every real browser hit
  files Web Vitals under the junk path. A redirect returns no HTML, so nothing reports. Check
  what a 404 page *carries* before calling a 404 the correct outcome.
- **`robots.ts` re-allows `/api/feed/`** — anything under that prefix stays crawlable,
  including accidental paths. Worth remembering when reasoning about why junk URLs persist.
- **Why the alias map could not have been a routing rule at first** — `1b450d3b` introduced it
  alongside the root catch-all `src/app/[slug]/page.tsx`, which resolved a bare sectionless
  slug through a slug index: request state, so no static pattern could express it. Only after
  `680e69bc` deleted that route did seven literal redirects become possible. A "why isn't this
  in the obvious place" question often has an expired constraint behind it, not an oversight.
- **Answer the question that was asked, then the one behind it** — the user's framing
  ("legacy paths, or something wrong in the code?") was a false dichotomy; the real answer was
  a third option, a two-day-old bug already fixed. Reconstructing it needed `git log -S` on the
  env var plus the post filenames to confirm the twenty-entry window, not a code read.
