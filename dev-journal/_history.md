# Rolling History — last 30 days (through 2026-08-22)

## Themes

- **Admin auth: from single gate to defense in depth** — 07-20's review flagged (and deliberately deferred) that `src/proxy.ts` middleware was the sole authorization boundary for all 12 admin routes. It became a real incident 07-26: the matcher's extension-exclusion regex was unanchored, so any path merely *containing* an excluded extension's substring (`.json` contains `.js`) bypassed the gate; fixed with `requireAdmin()` added to all 21 admin handlers plus a 32-char `SESSION_SECRET` floor (it had accepted any non-empty string, and the project's own docs said so). The gap resurfaced 08-12 in a different shape — admin edit pages' `generateMetadata` ran an unauthenticated DB read because `requireAdmin` covers only `/api/admin/*`, not the page namespace — closed with a shared `adminEditMetadata()` helper. 08-13 added `console.error` bypass logging with a shared `bypassId`. A 08-20 fix gave `guides/new`/`guide-topics/new` a real `requireAdminPageSession` body check for the same client-nav bypass class, but an independent 08-21 review found the fix incomplete in the worst way: `adminEditMetadata` only guards the `<title>` — it never stops a page body from rendering, since `generateMetadata` and the body are independent Next calls — so all four `[id]/edit` pages and the dashboard root (`/admin`, the page every protected page's nav links back into) still ran DB reads unauthenticated on the same bypass. Extended `requireAdminPageSession` to all six data-reading pages 08-21, added a real `adminPageContract.test.ts` assertion tying every page's body read to an actual guard call (not prose), and split tag constants into `adminTags.ts` to avoid a circular import while giving the guard a closed `AdminPageTag` union instead of a bare `string`. The 08-22 review then found that contract test could not fail for the case it was written for: it matched `source.includes("requireAdminPageSession(")`, which an unawaited call satisfies — and `requireAdminPageSession` only reaches its `redirect()` after `await verifySession()`, so a floating call lets the page's data read run first. Nothing else caught it (`eslint.config.mjs` uses `tseslint.configs.strict`, not `strictTypeChecked`, so `no-floating-promises` is off), and the function's own docblock had named the hazard without anything enforcing it. Closed 08-22 with an `await`-requiring assertion, verified by removing an `await` and confirming that test alone failed. - **08-21: accessibility hardening — reduced motion, and a lint gate for the rest** — `fadeUp` (`src/lib/client/motion.ts`), the shared entrance-animation factory behind 7 components, never checked `prefers-reduced-motion`, and neither did `ProjectFaq`'s chevron rotate, `BlogSectionHeader`'s `y` slides, `ExpandableSearch`'s `x` slide, or `ThemeToggle`'s `layoutId` pill — Framer's `MotionConfigContext` ships `reducedMotion: "never"`, so a `motion` component ignores the OS preference until something opts in. Fixed globally with a new `src/components/MotionPreferences.tsx` wrapping the app in `<MotionConfig reducedMotion="user">` from the root layout, over a `useFadeUp()` hook: one insertion point, covers everything animated, and can't be forgotten by a future component. The hook shape was also unsafe — returning `initial: false` under reduced motion contradicts the prerendered inline styles Framer SSRs, and `useReducedMotion()` reads `matchMedia` synchronously in the hook body, so the client's first render already disagrees. `eslint-plugin-jsx-a11y` added the same session; `jsxA11y.flatConfigs.recommended` can't be spread (flat config rejects the second `jsx-a11y` registration, since `eslint-config-next` registers the module namespace object), so the rules are enabled by id against next's registration, scoped to `**/*.tsx`. Of its 9 findings, 4 of 5 sites were false positives on deliberate workarounds — fixed in rule options; the one real finding replaced four `stopPropagation` calls in `ProjectImageLightbox` with a single `event.target === event.currentTarget` gate on the backdrop. - **08-22: third review pass, and the pattern that remediation introduces defects** — the daily `code-review` skill ran over the 18 commits of 08-21's remediation (`4c4e606..fb3f9f2`) and produced 9 findings + 3 coverage gaps, all fixed the same session (suite 2,312 → 2,319). Two were live-ish defects created *by* 08-21's fixes: the contract test's missing-`await` blind spot (see the admin-auth theme), and `errorDetails` — widened 08-21 from `{message, stack}` to a full own-enumerable spread for Prisma's `code`/`meta` — silently voiding its own "JSON-safe object" guarantee, since a `BigInt`, cycle, or function own property makes `JSON.stringify` throw *inside the log pipeline*, losing the original error entirely. Fixed by filtering each extra property through an `isJsonSerializable` check that defers to `JSON.stringify` in a `try`/`catch` rather than type-checking (a hand-rolled "is it a primitive" test rejects a `Date`, which `toJSON` makes perfectly serializable). Structural changes: `feedTag` moved from `content/feed.ts` to `db/posts.ts` beside `sectionTag` (the db layer had been importing up into content for a tag it owns; the feed route already imported `bySection` from there, so it cost no new dependency), and `stripComments` extracted to `src/test/sourceText.ts` for the three tests that assert on source text — the paginated route's `cache()` assertions were the worse instance, being *presence* checks a comment could have satisfied against a page that no longer wrapped anything. This is the third consecutive review over the same body of work; each pass found real defects in the previous pass's fixes.
